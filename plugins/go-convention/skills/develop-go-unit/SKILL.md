# develop-go-unit

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。`when` のある工程は、条件に当たるときだけ実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と、`skill:` 工程が指す skill の本文を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

Go の1単位を、「テストを書く → 赤を確かめる → 実装する → 緑を確かめる → 整える」の順で完成させる。読み終えると、どの層の単位でも、同じ TDD の判断で進められる。

この skill が持つのは、TDD の1単位としての判断だけである。テストの書き方は各層のテストの skill（test-domain-model、test-repository、test-usecase、test-handler）が、実装の形は各層の実装の skill（implement-domain-model、implement-repository、implement-query-service、implement-usecase、implement-handler）が、言語の形は write-go-code が、エラーは handle-errors が、ログは write-logs が持つ。この skill は、それらを順に呼んで一つの単位を仕上げるだけで、中身は変えない。

## 入力

単位の層と対象、その単位が主に担う BDD を持つ資料の絶対 path、既存のコードとテストがあればその path を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

## 判断基準

**単位を一つに固定する。** 一サイクルで完成させるのは、一つの層の一つの対象である。層は、`domain_model`、`repository`、`query_service`、`usecase`、`handler` のどれか一つに決める。単純なパターンの手順の口は `repository`、手順は `usecase` に当たる。同じ層の別の対象は、この単位を緑で閉じてから次の単位にする。

**赤を確かめてから実装する。** 赤の理由は、「対象がまだ無い（コンパイルエラー、未定義）」か「結果が期待と一致しない（assert の失敗）」のどちらかに分類できなければならない。Docker が無い、下の層のテストが赤、無関係なテストの失敗は、赤ではない。最初から緑なら、対象が実装済みか、テストが何も観測していない。

**実装の間、テストを変えない。** 実装中に `*_test.go` を編集しない。テストの誤りに気付いたら、実装を止めてテストの工程へ戻り、赤からやり直す。

**緑は、対象のテストと同じ package の全テストと機械検査。** 対象のテスト関数だけが通っても、緑ではない。

**整える前後で、振る舞いとテストを変えない。** 整える前後で同じテストが緑で、ケースの識別と期待を変えていない。

**テストの範囲は、その層が主に担うものだけ。** ほかの層が主に担う観点を、この単位のテストに足さない（apply-go-test-convention の BDD の写し方）。

## 手順

1. **単位を固定する（`fix-unit`）。** `references` があれば先に読む。層、対象、主に担う BDD、テストのファイルと実装のファイル、開始時のテストの結果を決める。
2. **テストを書く。** 層のテストの skill を、テストが先の場面として適用する。
3. **赤を確かめる（`run-red`）。** 対象のテスト関数を実行し、失敗の理由を分類する。
4. **実装する。** 層の実装の skill で、テストが緑になる最小の形を書く。テストは触らない。
5. **緑を確かめる（`run-green`）。** 対象のテスト、同じ package の全テスト、テストの規約の機械検査をすべて通す。
6. **整える（`refactor`）。** write-go-code で整える。この単位で具体エラーや境界の表を変えたなら handle-errors で、記録の場所やレベルを変えたなら write-logs で揃える。
7. **報告する（`report`）。**

## 停止条件

赤の理由が未実装でも不一致でもないときは、実装へ進まずに理由を返す。下の層の不足（usecase の単位なら usecase の不足）は、その層の単位へ返す。緑にならない原因が資料の不足なら、資料の持ち主へ返す。各 `skill:` 工程の停止条件に当たったら、その工程の報告に従って止まる。

止まるときは、書いた範囲（テストのファイル、実装のファイル）と書かなかった範囲を分け、どの工程で止まったか、返す先と必要な決定を報告に示す。

## 出力

単位（層、対象、主に担う BDD、ファイル）、赤の理由、緑の時点の機械検査の結果、整えた点と振る舞いを変えていない根拠、各 `skill:` 工程の報告、返した論点、次の単位の候補を報告する。
