# write-logs

中心にあるのは二つの考えである。**ログレベルは運用者に求める行動を表す。** ERROR が鳴ったら人が動き、WARN は増えたら見に行く。その意味を保つために、レベルはエラーの分類から表で一意に決める。**記録は一か所で一度だけにする。** 内側はエラーを返し、境界が拾って記録する。同じ失敗が層の数だけ並ぶと、件数が信用できなくなる。ログは監査記録の一次データではなく、消えてもよい二次情報である。業務の事実はイベントの行が持つ。

## レベルは分類から表で決める

INFO は、正しく拒んだか、記録するだけの出来事（RPC の完了、巡回の要約、起動と停止）で、誰も対応しない。WARN は、一件ずつはもう一度処理すれば通るが、増えたら容量か依存先を見に行く対象で、一件の WARN で人を呼ばない。ERROR は、すぐに人の介入が要るもので、出してよいのは回復不能（データか環境を直すまで解決しない）と分類不能（実装を直すまで解決しない）の二つだけである。業務上の拒否を ERROR にすると、対応が要る行と要らない行が同じ色で並び、ERROR を見る意味が無くなる。DEBUG が本番で出る前提の設計にしない。

| 分類 | レベル |
|---|---|
| 入力が不正、認証されていない、許可されていない、存在しない、すでに存在する、業務ルールに反する、利用上限に達した、未対応の操作、中断された | INFO |
| 同時更新で競合した、容量の上限を超えた、時間切れ、依存先が利用できない | WARN |
| 回復不能、分類不能 | ERROR |

表は `internal/crosscutting/log` に一つだけ置き、`log.Level(err)` で引く。表に分類が無いときの扱いは apply-crosscutting-contracts の契約に従う。分類不能の記録には `unclassified` の属性を真で足す。応答の表と処理の表（handle-errors）とは別の関心で、今の中身で WARN と「再処理で通りうる」が多く重なるのは偶然である。

## 返すなら記録しない、飲み込むなら記録する

エラーを返す場所は記録しない。返したエラーは最も外の境界が一度だけ記録する。エラーを飲み込んで先へ進む場所は、そのエラーが境界へ届かないので、飲み込んだ場所で一度だけ記録する。飲み込んでよいのは、失敗を一件に閉じ込める場面（一覧から壊れた一件を除く、巡回や発行で一件の失敗を記録して次へ進む）だけで、どの失敗を閉じ込めてよいかは処理の表の「全体に及ぶ」で決まる。記録して `return nil` するのは飲み込むことなので、その場面に当たらないなら `return err` にする。

層で言えば、記録するのは最も外の境界、一件ずつ処理して飲み込む手順と巡回、壊れた一件を除く Query の実装、取り消しの失敗を記録するトランザクションの管理だけである。command の usecase、リポジトリ、handler の本文は記録せずに返す。ドメインは `log/slog` を import しない。ドメインが運用者に伝えたいことは、エラーとコマンドの結果で外へ出る。

境界ごとの形は次のとおりである。RPC は、最も外の interceptor が RPC 一回につき一行を記録し、同じ interceptor が応答の Code への翻訳と panic の回収を行う。記録する `err` は翻訳の前のもので、原因はログにだけ残り、応答には公開してよい文言だけが出る。メッセージの受信境界は、一件につき一行を記録し、再処理させるか確定するかの判断を残す。常駐するワーカーは裸の `go` で起動せず、見張りの関数（`Supervise(ctx, name, logger, fn)`）が panic（stack 付き）と予期しない終了を ERROR で記録して、間隔を広げながら起動し直す。ctx の終了による停止は記録しない。プロセスの境界では、`run` が返したエラーを `main` が同じ表で分類して一度だけ記録し、停止の要求による終了は「中断された」として INFO にして正常の終了コードで終える。

## logger は注入する

logger は `main` で一つ作り、記録する構造体（interceptor、受信境界、ワーカー、一件ずつ処理する手順、壊れた一件を除く Query の実装、トランザクションの管理）へ組み立ての引数で渡す。記録しない構造体に logger のフィールドを置かない。フィールドがあれば誰かが使う。`slog.SetDefault` と `slog.Default()` に頼らず、ctx に logger を入れない。ctx で運ぶのは属性の元になる値（リクエストの識別子）だけで、ctx からその値を足す handler を logger に重ねる。その handler は `WithAttrs` も包み直す。包み直さないと `logger.With` の結果から外れる。テストでは `slog.New(slog.DiscardHandler)` を渡し、ログが出たかを確かめない。

## メッセージと属性

メッセージは、起きたことと取った行動を書く定型の一文で、値を埋め込まず、句点を付けない（「延滞の通知の一件を送れなかったため次へ進む」）。定型なら同じ出来事をメッセージで数えられる。値は属性に出し、キーは英語の snake_case で同じ意味に二つのキーを作らない。語彙の中心は `request_id`、`procedure`、`duration_ms`、`code`、`err`、`unclassified`、`panic`、`stack_trace`、`worker` で、業務の識別子（`loan_id`）はプロジェクトの語彙に足してから使う。属性は `slog.String` などの型付きの helper と `LogAttrs` で渡し、`slog.Any` は `err` と `panic` だけに使う。単位はキーに書いて値と一致させ、時刻は UTC で渡し、`slog.Group` で入れ子にしない。

値オブジェクトは、記録する行で値を取り出して渡す。何を出して何を伏せるかをその行で決めるためで、値オブジェクトに `String()` や `LogValuer` を持たせない。出してよいのは、業務の識別子、件数、時刻、Code である。個人を識別する値、トークン、認証のヘッダ、接続文字列は出さない。迷ったら「問い合わせの対応で他人に見せて困るか」で決める。

安全網として、logger を作るときに JSON の handler の `ReplaceAttr` で、キーを小文字にして区切りを除いた形が秘密の語（`password`、`token`、`secret`、`credential`、`authorization`、`cookie`、`session`、`apikey`、`privatekey`、`mail`、`phone`、`databaseurl`）を含むなら値を `[REDACTED]` にする。値の中身は走査しない。安全網が働いた行は、書いた側の判断を誤った印なので、書いた側を直す。秘密のキーを足したら、それが伏せられることを確かめるテストを一つ足す。

## 止まるとき

ドメインにログを求められたら、エラーかコマンドの結果で外へ出す設計を返す。記録して黙って成功を返したい要求が閉じ込めの場面に当たらないなら、`return err` の形を返す。ログを監査記録の一次データにする要求は、データモデルの資料へ返す。キーや言い回しの揺れでは止まらず、語彙に最も近いものを採る。
