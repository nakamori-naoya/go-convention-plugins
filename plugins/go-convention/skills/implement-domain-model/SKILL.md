# implement-domain-model

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

資料に書かれた集約、状態、コマンド、拒む理由を、そのまま Go の型、メソッド、具体エラーへ写す。読み終えると、usecase が「集約を見つける → コマンドを一回呼ぶ → 結果を適用する」だけで書けるドメインの package を書ける。

中心にあるのは二つの考えである。一つは、**業務の判断はコマンドの中にだけ置く**ことである。状態で受けるか拒むかは状態の型が決め、判断の材料は初期状態の型が持つ。usecase は型を調べず、判断しない。もう一つは、**資料が決め、コードはそれを写す**ことである。何を集約にし、何を拒むかは資料が決める。資料に無いものが要ると分かったら、書かずに資料へ返す。

## 入力

ドメインモデルの資料と業務知識の資料の絶対 path、写す対象の集約を受け取る。データモデルの資料があれば、イベントが持つ値の列を読むために、その絶対 path も受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約は、対象 repository の AGENTS.md / CLAUDE.md と `references` で渡される。

前提は Go 1.27 で、ドメインの package は標準ライブラリと、エラーの分類の package と、文脈共有の値オブジェクトの package だけを import する。

先に赤いテストがある場面も通常である。テストが使う名前とシグネチャを資料と突き合わせ、テストを変えずに緑にする実装を書く。テストが資料に無いものを要求していれば、実装で補わずに返す。

## 判断基準

### 何をどこから読むか

クラス図から要素と種類とコマンドの引数を、状態遷移図から状態とコマンドの受け方を読む。文からは図に無いもの（拒む理由と事前条件）だけを読み、拒む理由の正本は業務知識の「拒むときの理由」である。資料のコマンドの引数のうち、集約の外の事実の写しとそれを読む識別子は初期状態の型が持ち、業務の時刻と採番した識別子はメソッドの引数に残る。Find は読むだけで判断しない。提案の段階のものは写さない。詳しくは [資料の読み方](references/reading-the-model.md) を読む。

### 集約の形

初期状態の型は版を持たず、保存された状態の型は版を持つ。保存された状態の和型は、保存された状態が受けうるすべてのコマンドを持ち、受けない状態は資料の拒む理由を返す。コマンドは `<コマンド名>Result{Next; Event}` を返し、版を一つ進める。判断だけの公開メソッドは置かない。永続化ポートは集約と同じ package に置き、Find と `Apply<イベント名>` を基本にする。詳しくは [集約](references/aggregate.md) を読む。

### 値オブジェクトの形

非公開フィールドの struct を `New*` だけが作る。拒む値があるときだけ error を返す。`String()` や `slog.LogValuer` のような、表現と記録の形を実装しない。詳しくは [値オブジェクト](references/value-object.md) を読む。

完全な例は [例：図書館の貸出](references/example-library.md) にある。書き始める前に一度読む。

## 手順

1. **資料を読み、対応を決める。** `references` があれば先に読む。クラス図と状態遷移図から、型の一覧（値オブジェクト、初期状態の型、保存された状態の型、イベント）と、コマンドごとの受ける状態と拒む状態を決める。拒む状態ごとに、業務知識の拒む理由を対応させる。理由が無い組と、提案の段階のものを、止まる候補として分ける。
2. **値オブジェクトを書く。** 識別子と、資料の値オブジェクトを書く。
3. **集約を書く。** 初期状態の型、保存された状態の型、和型、`Restore*`、コマンド、結果の型を書く。
4. **エラーとイベントを書く。** 拒む理由から具体エラーを、資料のイベントからイベントの型を書く。イベントの値の列は、データモデルの資料のイベント表から決める。
5. **永続化ポートを書く。** Find と `Apply<イベント名>` の interface を書く。
6. **機械検査を通す。**
   ```bash
   gofmt -l ./<domain package>
   go vet ./<domain package>/...
   go tool golangci-lint run ./<domain package>/...
   ```
   `gofmt -l` の出力が空で、linter はドメインが `log/slog`、pgx、connect、JSON を import していないことと、和型の型スイッチの網羅を確かめる。
7. **報告する。** 出力の項目を返す。

## 停止条件

受けない状態の拒む理由が資料に無い組があれば、そのコマンドを和型に置かずに止まり、資料への提案として返す。資料に無いコマンド、状態、拒む理由が要ると判断したときも、書かずに返す。提案の段階のもの（まだ業務知識に無い用語や拒む理由）は、書かずに提案の確定を待つ。資料の業務の時刻の引数が時点で受けられないとき（日付しか決まっていない）は、資料の持ち主へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

名前の揺れ（資料に語の無い初期状態の型の名前）や、資料が順を決めていない事前条件の順では止まらない。最も筋の良い形を仮説として採り、報告に示し、名前は資料への提案に含める。

## 出力

資料の要素、状態、コマンド、拒む理由と、Go の型、メソッド、具体エラーの対応、書かずに止めたもの（理由が無い組、提案の段階のもの）と返し先、仮置きしたもの、機械検査の結果を報告する。

機械検査が通って言えるのは、フォーマット、vet、ドメインの import の禁止、和型の型スイッチの網羅に違反が無いことだけである。資料の要素と型が一対一か、拒む理由が業務知識と一致するかは、対象を読んで報告する。
