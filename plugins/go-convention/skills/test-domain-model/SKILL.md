# test-domain-model

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

ドメインの package（集約、値オブジェクト、イベント）が資料どおりに判断するかを、メモリの上の値だけで確かめる。読み終えると、ドメインのテストが主に担う BDD を、どのテスト関数にどう書くかを決められる。

中心にあるのは一つの考えである。**ドメインのテストは、判断だけを確かめる。** 判断はコマンドの中にあり、材料は初期状態の型が持つので、Given に値を並べ、コマンドを一回呼び、結果を比べるだけで書ける。DB、mock、手順は要らない。

テストの形（表、識別、Given、Then）と、BDD を主に担うテストだけが資料の ID を名乗る規則は、apply-go-test-convention に従う。

## 入力

業務知識の資料とドメインモデルの資料の絶対 path、対象のドメインの package を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

テストを書く場面は二つあり、どちらも通常である。実装が先にある場面では、対象の公開 API を読んで書く。テストが先の場面では、資料と implement-domain-model の形（初期状態の型、状態の型、和型のコマンド、`<コマンド名>Result`、具体エラー）から名前とシグネチャを決めて書き、コンパイルエラーで赤になる状態を正とする。

## 判断基準

### 何をテストするか

値オブジェクトの生成の条件と判定、生成のコマンド、状態ごとの和型のコマンド（受ける状態と受けない状態）、拒まないコマンドの両側、引き継ぐ値と進む版をテストする。値を取り出すだけの検証、永続化、同時実行、材料を集めること、手順、本人の確認はテストしない。詳しくは [何をテストするか](references/what-to-test.md) を読む。

### どの BDD を、どのテスト関数に置くか

ドメインのテストが主に担う BDD だけを、資料の ID で写す。テスト関数は状態遷移図から決まる。生成のコマンドは初期状態の型のテストに、和型のコマンドは状態の型ごとのテストに置く。提案の段階にあってどのテストも担えない BDD は、理由を付けて列挙する。詳しくは [資料からの割り振り](references/mapping-from-doc.md) を読む。

### 表の形

Given は初期状態の型と `Restore*` と `New*` の値、When はコマンドの引数、Then は `wantNext`（`Restore*` で組む）、`wantEvent`（射影の struct）、`wantErr`（具体エラー）である。完全な例は [テーブルの形](references/table-shape.md) にある。

## 手順

1. **資料と対象を揃える。** `references` があれば先に読む。業務知識の BDD と、ドメインモデルの状態遷移図と、対象の公開 API（テストが先なら、資料から決めた名前とシグネチャ）を並べる。
2. **BDD を割り振る。** 各 BDD を、ドメインのテストが主に担うか、ほかのレベルが主に担うか、どのテストも担えないかに分ける。主に担うものを、テスト関数に割り振る。
3. **テスト関数ごとに表を書く。** 割り振った BDD を資料の順に写し、資料に無いケース（具体エラーごと、境界の両側、理由を同時に破る組の順、`false` 側）を生成した id でその後ろに足す。資料の ID を写したファイルに、資料の宣言を一つ書く。どのテストも担えない BDD があれば、列挙する。
4. **ループ本体を一回書く。**
5. **機械検査を通す。** テストが先の場面では、`go vet` と `go test` は対象の未実装のコンパイルエラーで失敗する。これは赤であり停止ではない。失敗の理由が未実装であることを確かめ、形と網羅の検査だけを通す。
   ```bash
   go vet ./<domain package>/...
   go test -shuffle=on -count=1 ./<domain package>/...
   go test -count=1 -run 'TestPendingLoan_Borrow/BDD-001_' ./<domain package>/...
   ```
   テストの形の検査（`check-cases.py`）と、repository 全体の BDD の網羅の検査（`check-bdd-coverage.py`）は、apply-go-test-convention の tool で行う。
6. **報告する。** 出力の項目を返す。

## 停止条件

対象の実装が既にあるのに、資料のコマンドに対応する公開のメソッドが無い、または拒む理由の具体エラーが無いときは、テストで補わずに implement-domain-model へ返す。対象が Clock を読む、採番する、時刻を引数で受けないときは、期待が決まらないので implement-domain-model へ返す。Given を書くのに `setup` や操作列や DB が要ると思ったら、対象はドメインの外の手順なので、書かずに返す。資料に無い拒否を確かめたくなったら、書かずに資料へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

ケースの名前や並びの揺れでは止まらない。資料の BDD の順と語に最も近い形を採り、報告に示して進む。

## 出力

テスト関数の一覧と、各関数が主に担う BDD の ID、ほかのレベルが主に担う BDD とその担い手、どのテストも担えない BDD と理由、資料に無いケースで埋めた観点、機械検査の結果、返した論点と返し先を報告する。

機械検査が通って言えるのは、テストの形と、repository 全体の BDD の網羅の構造だけである。割り振りが資料の文と一致するか、`wantNext` が版だけを進めているかは、対象を読んで報告する。
