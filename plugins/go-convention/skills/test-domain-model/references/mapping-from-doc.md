# 資料からの割り振り

# どの BDD を主に担うか

資料の BDD を `id` に写すのは、それを主に担うテストだけである（apply-go-test-convention の規則）。ドメインのテストが主に担うのは、`Then:` が、コマンドが受けるか拒むか、次の状態、発するイベント、値の生成の条件を観測する BDD である。

図書館の貸出では、業務知識の BDD が次のように割り振られる。借りる場面の BDD-001〜004 は `TestPendingLoan_Borrow` に、返す場面の BDD-007 は `TestOnLoan_Return`、BDD-008 は `TestOverdueLoan_Return`、BDD-009 は `TestReturnedLoan_Return` に、延滞にする場面の BDD-010 と BDD-011 は `TestOnLoan_MarkOverdue` に置く。

ほかのレベルが主に担う BDD は、ここでは写さない。本がほかの利用者に貸出中（BDD-005）と、同じ本を二人が同時に借りる（BDD-013）は、貸出を記録する側が守るので、永続化層のテストが主に担う。他人の利用者カード（BDD-006）は、呼び手が本人を確かめる段階で拒むので、handler のテスト（API のテスト）が主に担う。どちらが担うかは、ドメインモデルの資料の文（「貸出を記録する側が保証する」「呼び手が本人を確かめる段階で拒む」）から読める。

返却済みの貸出は延滞にならない（BDD-012）は、その拒む理由が資料で提案の段階にあり、`MarkOverdue` を和型に置けないので、どのテストも担えない。これは、どのテストも担わない BDD として、理由（拒む理由が業務知識への提案の段階にある）を付けて列挙する。提案が確定したら、`TestReturnedLoan_MarkOverdue` に置く。

# どのテスト関数に置くか

状態遷移図から、テスト関数が決まる。

`[*]` から出る矢印の生成のコマンドは、初期状態の型のメソッドなので、`Test<初期状態の型>_<コマンド>`（`TestPendingLoan_Borrow`）に置く。

それ以外のコマンドは、保存された状態の和型のメソッドで、状態ごとの型が実装する。テスト関数は、状態の型ごとに一つずつ置く（`TestOnLoan_Return`、`TestOverdueLoan_Return`、`TestReturnedLoan_Return`）。受ける状態のテストに、受ける BDD を置く。受けない状態のテストに、その状態で拒む BDD を置く。状態の型は別の型なので、テスト関数を分けても「対象一つにテスト関数一つ」を守っている。

BDD の `Then:` が値オブジェクトの判定そのもの（ある値とある値が重なるか）だけを観測するなら、その値オブジェクトのメソッドのテストに置く。`Then:` がコマンドの結果（延滞になる、ならない）を観測するなら、コマンドのテストに置き、値オブジェクトの境界（`TestDue_PassedAt` の当日と翌日）は生成した id のケースで確かめる。

一つの BDD が二つのコマンドを通るなら、`Then:` が観測するコマンドのテストに置く。

# 写し方

資料の ID、見出し、gherkin は、apply-go-test-convention の規則でそのまま `id`、`name`、`description` に写す。資料の ID を写したテストファイルには、`// BDD の資料: <repository 相対の path>` を一つだけ書く。

`description` の `Then:` に、このテストでは観測できない行（別の貸出が生まれない、記録された行）があっても、削らない。その行は、それを主に担う別のレベルのテストが観測する。
