# develop-usecase

[工程順序の正本](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と、`skill:` 工程が指す入口の本文を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

これは、**usecase 層の 1 単位を「テストを書く → 赤を確かめる → 実装する → 緑を確かめる → 整える」の順で完成させる合成の入口**である。1 単位は、domain-rule 資料の業務イベント 1 つに対応する command の usecase、または一覧・表示 1 つに対応する query の usecase である。テスト file（`*_test.go`）と実装 file は分かれたままで、この入口は両者を交互に書く順序と、その間の判断だけを持つ。

これは、**テストの書き方や実装の形を新たに決めるものではない**。5 観点の配線をどう確かめるかは usecase のテストの規約が、command / query の形と tx の張り方は usecase の実装の規約が、言語レベルの形は言語規約が、層境界での包み方はエラーの規約が持つ。それぞれは `playbook.yml` の `skill:` 工程が指し、この入口はそれらを変えない。業務ルール（集約・VO）、SQL とリポジトリ、RPC の入口は別の単位の入口が扱う。

前提: Go 1.27・pgx/v5・dockertest・testify・Docker daemon。ドメインの実装、リポジトリまたは query service の実装、永続化層のテスト支援（`rdbtest`）が確定している。

## 入力

- domain-rule 資料と domain-model 資料の絶対pathと、この単位で完成させる業務イベント（command）または一覧・表示（query）1 つ。
- ドメインの実装、永続化の実装、`rdbtest` のpath。既存のcodeとテストがあればそのpath。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

## 判断基準（TDD の 1 単位）

| 観察対象 | 述語 |
|---|---|
| 赤の理由 | `run-red` で対象のテスト関数が失敗し、その理由が「usecase の型・`Execute`・Input / Output がまだ無い（コンパイルエラー）」か「返り値または DB の状態が期待と一致しない（assert の失敗）」のどちらかに分類できる。Docker が無い、下の層のテストが赤、`rdbtest` の `Seed*` / `Read*` や `IDGenerator` の固定実装が無い、無関係なテストの失敗は赤ではない |
| 実装中のテスト | `implement` の間、`*_test.go` を編集していない。テスト支援の不足に気付いたら実装を止め、`write-failing-test` へ戻り、それでも足りないものは永続化層の規約へ返す |
| 緑の範囲 | `run-green` で、対象のテスト関数と同じ package の全テストが通り、usecase のテストの規約が求める機械検査（`go vet`・単独実行・テストの形）も通る |
| 整える前後 | `refactor` の前後で同じテストが緑で、テストの `id` / `name` / `description`・`want*` を変えていない |
| テストの範囲 | テストのケースは、5 観点（入力解決・協調・ソース選択・tx 境界・呼び分けと永続化）の相異なる配線分岐だけ。業務ルールの境界値、全テーブルの突き合わせ、proto 変換をここで足さない |
| 単位の大きさ | 1 サイクルで完成させるのは usecase 1 つ。複数集約の協調で別の usecase が要ると分かったら、この単位を緑で閉じてから次の単位を始める |

## 手順

1. **単位を固定する（`fix-unit`）。** `references` があれば先に読む。対象の業務イベント（または一覧）を 1 つに決め、command か query か、呼ぶ集約の操作とポート、Input / Output の primitive を列挙する。テスト file と実装 file の名前（実装 file と 1 対 1）を決め、既存なら現在の `go test` の結果を記録する。完了条件: usecase 名が資料の業務語で 1 つ、種類、呼ぶ操作とポート、`Input` / `Output` とコンストラクタ名、予定した `Execute` の手順、テスト file と実装 file のpath、開始時のテスト結果が 1 行ずつ言える
2. **テストを書く（`write-failing-test`）。** usecase のテストの規約に、資料と単位（usecase 名、種類、呼ぶ操作とポート、Input / Output、予定した `Execute` の手順）を渡し、テストが先の場面として適用する。その規約が返すのは、5 観点の配線分岐を写したテスト file と、対象未実装による赤の記録である。完了条件: 各配線分岐が 1 ケース以上で観測でき、テスト file が保存され、`go test` の失敗理由が記録されている
3. **赤を確かめる（`run-red`）。** Docker が動く環境で `go test -count=1 -run '<テスト関数>' ./<package>/...` を実行し、失敗の理由を上の表で分類する。完了条件: 失敗の理由が「対象未実装」または「期待と一致しない」で、それ以外の失敗が無い
   ```bash
   go test -count=1 -run 'TestConfirmReservation_Execute' ./usecase/...   # 対象のテスト関数だけ
   ```
4. **実装する（`implement`）。** usecase の実装の規約に従い、command なら「入力の解決 → tx を張る → 復元または生成 → 絞り込み → 操作 → 保存」、query なら「読み取りポートを呼んで DTO を返す」の形で書く。テストが緑になる最小の実装で、`*_test.go` は触らない。完了条件: `Execute` の各行が 5 観点のどれかに割り当てられ、どれにも割り当てられない行（状態の判定・件数の解釈・計算）が無い
5. **緑を確かめる（`run-green`）。** 対象のテスト関数、同じ package の全テスト、usecase のテストの規約の機械検査をすべて通す。完了条件: 次が全部通り、Docker が無いときは skip ではなく失敗として現れる
   ```bash
   go vet ./...
   go test -count=1 ./<package>/...
   go test -count=1 -run '<テスト関数>/<id>_' ./<package>/...   # 足したケースを 1 つずつ単独で
   ```
6. **整える（`refactor`）。** 言語規約で関数の形・型と interface・名前・標準ライブラリを揃える。振る舞いは変えず、テストは触らない。完了条件: 言語規約の機械検査が通り、手順 5 と同じテストが緑
7. **エラーを揃える（`align-errors`。この単位で層境界の包み方や usecase 固有のエラーを足した・変えたときだけ）。** エラーの規約で、層境界で 1 回だけの `%w` と、`errors.Is` で判定できる形を揃える。完了条件: 包みが境界 1 回で、テストが緑
8. **報告する（`report`）。** 下の「報告」の項目

## 停止条件

止まるのは、資料または規約の契約に反する要求、正本に無い決定が要る、利用者の許可が要る、toolが失敗した、のどれかに当たるときで、それ以外の判断の揺れでは止まらない。

- `run-red` で対象のテストが最初から緑 → 対象が実装済みか、テストが配線を観測していない。実装へ進まず、どちらかを確かめてテストの工程へ戻る
- `run-red` の失敗理由が対象未実装以外（Docker が無い、下の層のテストが赤、`rdbtest` や `IDGenerator` の固定実装が無い、無関係なテストの失敗）→ 実装へ進まない。理由を返して止まる（下の層の不足は永続化層の単位へ返す）
- `run-green` で緑にならず、原因がテストの誤り → 実装を止め、`write-failing-test` へ戻って直し、`run-red` からやり直す（これは停止ではなく戻り）
- `run-green` で緑にならず、原因が集約の操作やポートの不足（usecase から呼ぶ API が無い）→ 止まり、ドメインまたは永続化のどの単位へ返すかを示す
- 各 `skill:` 工程が持つ停止条件に当たった → その工程の報告に従って止まる

止まるときは、書いた範囲（テスト file・実装 file）と書かなかった範囲を分け、どの工程で止まったか、返す先（資料、規約、利用者）と必要な決定を報告に示す。

判断の揺れでは、その時点の根拠から最も筋の良い形を仮説として採り、仮説であることと採らなかった形を報告に明示して進む。

- 複数集約の協調を同じ tx で行うか、ドメインイベントを受けた別の usecase で行うかが資料から一意に決まらない: 資料が時間差を明記していなければ同じ tx の形を仮説として採り、報告に示す。

## 報告

- 単位（usecase 名、種類、呼ぶ操作とポート、テスト file と実装 file）
- 赤の理由と、緑になった時点の機械検査の結果
- 整えた点（言語規約・エラーの規約で変えたもの）と、振る舞いを変えていないことの根拠（同じテストの緑）
- 各 `skill:` 工程の報告
- 停止条件に当たって返した論点、次の単位の候補
