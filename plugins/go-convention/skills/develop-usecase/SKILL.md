# develop-usecase

command の流れ（見つける、一回呼ぶ、適用する）、トランザクションの所有、Outbox、失敗の閉じ込めの一般則とその理由は、development-convention の `apply-layer-convention` が持つ。ここが持つのは、それを Go で書く形と、usecase のテストが何を確かめるかである。**usecase は判断を持たない**ので、テストは配線と境界だけを確かめる。

進め方と赤は `develop-inside-out` に、`tx.Manager`、採番器、`HandlingOf`、`Level` の契約は apply-crosscutting-contracts に、テストの共通の形は apply-go-test-convention に従う。例は [例：図書館の貸出の usecase](references/example.md) にある。

## command の形

一つの業務イベントに、一つの型と一つの `Execute` を置き、名前は資料の業務の語にする。入力は値オブジェクトを並べた `<usecase名>Input` で受けて検証しない。依存は `tx.Manager`、ドメインの永続化ポート、採番器、自分が所有する外部の境界のポートだけで、読み取りのポートは import しない。型スイッチ、状態の比較、件数や時刻の解釈を書かない。コマンドが和型に置けていない間は、その usecase を書かない。

`Execute` は、`tx.Manager.Run` の中で Find、コマンドを一回、`Apply` を呼ぶ。応答で返す識別子は `Run` の前に採番する。出力はコマンドの結果のイベントから作る。`(Result, bool)` の `false` は何も起きなかったことなので、`Apply` を呼ばずに nil を返す。エラーは包まずに返し、記録しない。業務の時刻は入力で受けるので時計を持たず、要求ごとに変わらない設定の値オブジェクト（暦）はコンストラクタで受ける。

物理設計の指定は、名前のある `tx.Options` の変数に写し、上のコメントに物理設計のどの節から写したかを書く。自分で分離レベルを選ばず、やり直しのループも書かない。

```go
// borrowTxOptions は、物理設計の「分離性判断: 貸出上限」の指定である。SERIALIZABLE で、直列化の失敗だけを最大3回やり直す。
var borrowTxOptions = tx.Options{Isolation: tx.Serializable, RetryOn: tx.SerializationFailure, MaxRetries: 3}
```

資料が二つの集約を同じ時点で成立させると定めたときだけ、`orchestration/usecase/command` に一つの `Run` で二つを操作する command を置き、先のコマンドの結果を値として次のコマンドへ渡す。usecase が usecase を呼ばない。

## 手順の形（単純なパターン）

手順は、自分が所有する口を順に呼び、集約を作らない。依存は `tx.Manager`、自分の口、外部へ送るポート、飲み込む失敗を記録する logger である。候補を選ぶ、一件を回収する、送ったことを記録する、失敗を記録する、はそれぞれ別の `Run` で確定させ、外部への送信はどの `Run` の外でも行う。外部へ送るポートには要求の識別子を冪等の鍵として渡す。送った後で記録に失敗すると、もう一度送られるからである。

一件の失敗は、`HandlingOf` の「全体に及ぶか」が真か表に無ければ残りを試さずに返す。一件に閉じた失敗は、「再処理で通りうる」なら記録せずにリースが切れた後の回収に任せ、通らないなら口で失敗を記録し、どちらも飲み込む場所で `Level` のレベルで一度だけログに残す。回収の回数の上限との比較は手順が行う。業務の判断が要ると分かったら書かずに返す。

## query の形

query の usecase は、自分の package が所有する読み取りのポートを呼んで読み取りモデルを返し、トランザクションを張らない。入力からどのポートを呼ぶかを選ぶのは usecase の関心で、SQL、並び、集計は Query の実装の関心である。

## テスト：配線と境界だけを、実物で確かめる

実物の PostgreSQL、リポジトリ、トランザクションの管理を本番と同じコンストラクタで組み、時計、採番器、外部の境界のポートだけを gomock で差し替える。前提は持ち主の書き込み経路で作り、観測するのは返り値と、観点が見るテーブルだけにする。主に担う BDD は、`Then:` が、複数の書き込みが同じ確定で起きること、手順の順序、一件ごとの確定を観測するものである。

command では四つを確かめる。**配線と保存**は、代表的な一つのケースで、見つける、呼ぶ、適用するを通ってコマンドの結果が保存されること。**トランザクションの境界**は、一つの確定に入るべき書き込み（延滞と通知の要求）が両方そろって確定し、途中の書き込みが失敗したら先の書き込みも残らないこと。途中の失敗は、実物を壊れた状態にして起こし（先に同じ版を記録して後の書き込みを一意制約の違反にする）、偽のリポジトリで失敗を返させない。**拒否の伝わり方**は、代表的な一つの拒否で、何も保存せずに具体エラーを返すこと。**業務の時刻と識別子**は、入力の時刻と採番した識別子がそのまま出力と保存に使われること。

手順では、途中の一件が失敗してもそれより前の確定が残ること、外部へ送るポートの mock が呼ばれた時点でその件の回収が確定していること、一件に閉じた失敗で次へ進み全体に及ぶ失敗で残りを試さないこと、再処理で通らない失敗が恒久失敗として記録されること、冪等の鍵が渡ることを確かめる。

確かめないのは、入力の検証、拒否の理由の網羅（ドメイン）、行の全列と制約の翻訳（永続化）、Code と文言と認可（入口）、ログが出たか、物理設計のやり直し（同時の割り込みを順に再現できないので、トランザクションの管理と永続化のテストが持つ）である。同じ実 DB を共有するので直列で走らせる。

## 機械検査

```bash
go build ./... && go vet ./...
go tool golangci-lint run ./...
go test -count=1 ./<usecase package>/...
```

usecase の package が pgx、sqlc の生成型、connect、proto を import していないことと、command の package が読み取りの package を import していないことも確かめる。

## 止まるとき

usecase で状態を見て分岐したくなったとき、集約に無いコマンドを呼びたくなったとき、コマンドが和型に置けていないとき、物理設計に指定が無いとき、二つの集約を同じ時点で成立させるかが資料に無いとき、外部の受け手が冪等を約束できないとき、トランザクションの境界の途中の失敗を実物で起こせないときは、書かずに持ち主か資料へ返す。報告には、usecase の形、入力と出力と依存、`tx.Options` と物理設計の根拠、手順ならトランザクションの区切りと冪等の鍵、確かめた観点、テストが主に担う BDD の ID を書く。
