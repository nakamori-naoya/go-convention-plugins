# develop-handler

[工程順序の定義](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と、`skill:` 工程が指す入口の本文を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

これは、**handler 層の 1 単位を「テストを書く → 赤を確かめる → 実装する → 緑を確かめる → 整える」の順で完成させる合成の入口**である。1 単位は、proto の `service` にある RPC 1 つと、それが呼ぶ usecase 1 つの対である。テスト file（`*_test.go`）と実装 file は分かれたままで、この入口は両者を交互に書く順序と、その間の判断だけを持つ。

これは、**テストの書き方や実装の形を新たに決めるものではない**。公開 API として何をどう確かめるかは handler のテストの規約が、server 実装・変換関数・interceptor・組み立てと起動は handler の実装の規約が、言語レベルの形は言語規約が、sentinel から `connect.Code` への対応表はエラーの規約が、interceptor が 1 回だけ出すログはログの規約が持つ。それぞれは `playbook.yml` の `skill:` 工程が指し、この入口はそれらを変えない。業務判断、tx、永続化、usecase の配線は別の単位の入口が扱う。

前提: Go 1.27・connect v1.21.0・protobuf・pgx/v5・dockertest・testify・Docker daemon。usecase の実装と、その下の層のテストが緑である。

## 入力

- proto と生成code、この単位で完成させる RPC 1 つ、呼ぶ usecase の型と `Execute` の入出力。RPC ごとの BDD を持つ API 仕様の資料があればその絶対path。
- `run` が呼ぶ組み立て関数、公開エラー対応表、`rdbtest` のpath。既存のcodeとテストがあればそのpath。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

## 判断基準（TDD の 1 単位）

| 観察対象 | 述語 |
|---|---|
| 赤の理由 | `run-red` で対象のテスト関数が失敗し、その理由が「server の RPC メソッド・変換関数・対応表の行がまだ無い（コンパイルエラー、または `CodeUnimplemented`）」か「返った `connect.Code`・公開文言・レスポンス・DB の反映が期待と一致しない（assert の失敗）」のどちらかに分類できる。Docker が無い、usecase のテストが赤、組み立て関数が引数で依存を受けていない、無関係なテストの失敗は赤ではない |
| 実装中のテスト | `implement` の間、`*_test.go` を編集していない。組み立て関数の差し替え点の不足に気付いたら、それは実装の規約の範囲なので実装で直し、テストは変えない |
| 緑の範囲 | `run-green` で、対象のテスト関数と同じ package の全テストが通り、handler のテストの規約が求める機械検査（`go vet`・単独実行・ケース識別）も通る |
| 整える前後 | `refactor` の前後で同じテストが緑で、テストの `id` / `name` / `description`・`wantCode` / `wantMessage` / `want*` を変えていない |
| テストの範囲 | テストのケースは、その RPC が公開する結果（成功・sentinel ごとの Code と文言・主体無し・他人・入力不正）だけ。業務の境界値、全テーブルの突き合わせ、usecase の 5 観点をここで足さない |
| 単位の大きさ | 1 サイクルで完成させるのは RPC 1 つ。同じ service の別の RPC は、この単位を緑で閉じてから次の単位を始める |

## 手順

1. **単位を固定する（`fix-unit`）。** `references` があれば先に読む。対象の RPC を 1 つに決め、呼ぶ usecase と Input / Output、返しうる sentinel と対応表の Code を列挙する。テスト file（server 実装のファイル名に `_test`）と実装 file の名前を決め、既存なら現在の `go test` の結果を記録する。完了条件: RPC 1 つ、usecase との 1:1、公開結果の一覧と各 sentinel の `wantCode`、組み立て関数の有無、テスト file と実装 file のpath、開始時のテスト結果が 1 行ずつ言える
2. **テストを書く（`write-failing-test`）。** handler のテストの規約に、proto と単位（RPC、usecase の入出力、公開結果の一覧と `wantCode`）を渡し、テストが先の場面として適用する。その規約が返すのは、公開結果ごとのケースを持つ API テスト file（起動と組み立てのテスト支援を含む）と、対象未実装による赤の記録である。完了条件: 公開結果の一覧の各項目がケースに対応し、テスト file が保存され、`go test` の失敗理由が記録されている
3. **赤を確かめる（`run-red`）。** Docker が動く環境で `go test -count=1 -run '<テスト関数>' ./<package>/...` を実行し、失敗の理由を上の表で分類する。完了条件: 失敗の理由が「対象未実装」または「期待と一致しない」で、それ以外の失敗が無い
   ```bash
   go test -count=1 -run 'TestReservationServer_ConfirmReservation' ./handler/...   # 対象のテスト関数だけ
   ```
4. **実装する（`implement`）。** handler の実装の規約に従い、server の RPC メソッド、proto と usecase の往復の変換関数、対応表の行、必要なら interceptor と組み立ての配線を書く。テストが緑になる最小の実装で、`*_test.go` は触らない。完了条件: RPC が usecase を 1 つ呼び、変換が項目ごとに写され、対応表からその RPC の sentinel が全部引ける
5. **緑を確かめる（`run-green`）。** 対象のテスト関数、同じ package の全テスト、handler のテストの規約の機械検査をすべて通す。完了条件: 次が全部通り、単独実行でも通る
   ```bash
   go vet ./...
   go test -count=1 ./<package>/...
   go test -count=1 -run '<テスト関数>/<id>_' ./<package>/...   # 足したケースを 1 つずつ単独で
   ```
6. **整える（`refactor`）。** 言語規約で関数の形・型と interface・名前・標準ライブラリを揃える。振る舞いは変えず、テストは触らない。完了条件: 言語規約の機械検査が通り、手順 5 と同じテストが緑
7. **エラーを揃える（`align-errors`。この単位で対応表の行や公開文言を足した・変えたときだけ）。** エラーの規約で、sentinel と `connect.Code` の対応表が境界 1 か所で、文言が sentinel の `.Error()` から来る形を揃える。完了条件: 対応表が 1 か所で、テストが緑
8. **ログを揃える（`align-logs`。この単位で interceptor やログの出力を足した・変えたときだけ）。** ログの規約で、最外の interceptor が 1 回だけ、レベル表と属性語彙に従って出す形を揃える。完了条件: RPC 1 回につき記録が 1 か所で、テストが緑
9. **報告する（`report`）。** 下の「報告」の項目

## 停止条件

止まるのは、資料または規約の契約に反する要求、正式な定義に無い決定が要る、利用者の許可が要る、toolが失敗した、のどれかに当たるときで、それ以外の判断の揺れでは止まらない。

- `run-red` で対象のテストが最初から緑 → 対象が実装済みか、テストが公開結果を観測していない。実装へ進まず、どちらかを確かめてテストの工程へ戻る
- `run-red` の失敗理由が対象未実装以外（Docker が無い、usecase のテストが赤、無関係なテストの失敗）→ 実装へ進まない。理由を返して止まる（usecase の不足は usecase の単位へ返す）
- `run-green` で緑にならず、原因がテストの誤り → 実装を止め、`write-failing-test` へ戻って直し、`run-red` からやり直す（これは停止ではなく戻り）
- `run-green` で緑にならず、原因が usecase の入出力や sentinel の不足（RPC から写せない）→ 止まり、usecase またはエラーの規約へ返す
- RPC が 2 つの usecase を要る、または usecase が無い → 止まり、usecase の単位へ返す
- 各 `skill:` 工程が持つ停止条件に当たった → その工程の報告に従って止まる

止まるときは、書いた範囲（テスト file・実装 file）と書かなかった範囲を分け、どの工程で止まったか、返す先（資料、規約、利用者）と必要な決定を報告に示す。

判断の揺れでは、その時点の根拠から最も筋の良い形を仮説として採り、仮説であることと採らなかった形を報告に明示して進む。

- 入力不正の公開文言が資料に無い: 変換関数が返す sentinel の文言をそのまま公開する形を仮説として採り、報告に示す。

## 報告

- 単位（RPC、usecase、公開結果の一覧、テスト file と実装 file）
- 赤の理由と、緑になった時点の機械検査の結果
- 整えた点（言語規約・エラーの規約・ログの規約で変えたもの）と、振る舞いを変えていないことの根拠（同じテストの緑）
- 各 `skill:` 工程の報告
- 停止条件に当たって返した論点、次の単位の候補
