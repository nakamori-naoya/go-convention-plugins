# develop-handler

中心にあるのは二つの考えである。**値オブジェクトへの変換と業務の時刻の取得は、入口で一度だけ行う。** usecase は検証済みの値だけを受け取る。**入口は判断せず、記録せず、翻訳しない。** 判断は集約が、翻訳と記録は最も外の interceptor が一度だけ行う。

進め方と赤は `develop-inside-out` に、表を引く関数の契約は apply-crosscutting-contracts に、応答の表は handle-errors、記録は write-logs、テストの共通の形は apply-go-test-convention に従う。前提は `connectrpc.com/connect` v1 である。例は [例：本を借りる RPC](references/example.md) にある。

## 入口

要求のプリミティブは、入口で値オブジェクトへ変換して usecase の入力に詰め、欠けた値を既定値へ丸めない。業務の時刻は入口が時計から一度だけ取る。要求の本文から時刻や主体を受け取らず、主体は認可の interceptor が解決して ctx に載せたものを使う。資源の持ち主と主体の一致のような判断は、集約のコマンドの事前条件にする。

handler の本文は、一つの usecase を呼び、エラーを `return nil, err` でそのまま返す。`errors.Is` で分岐せず、`connect.NewError` を作らず、記録しない。応答への写しは `<元>To<先>` の変換の関数に置き、値を取り出して詰めるだけにする。

巡回の相手が command なら、巡回が始めに時刻を一度だけ取り、query の usecase で候補を選び、一件ずつ command を呼び、ループと閉じ込めと記録を持つ。相手が手順なら、巡回は手順の `Execute` を一度呼ぶだけにする。受信境界は、メッセージを契約の型へ変換して手順を呼び、処理の表の「再処理で通りうるか」で受け取りを確定するか再処理させるかを決めて記録する。

## interceptor の並び

外から、記録と翻訳、認証、認可、頻度の制限の順に並べる。最も外の interceptor が、リクエストの識別子を ctx に載せ、panic を回収し、RPC 一回につき一行を記録し、エラーを応答の Code と公開の文言へ翻訳する。同じエラーから Code とレベルを一度に決めるために、翻訳と記録を一つに置く。内側で `connect.Error` が作られていたら分類不能として扱う。

認証の interceptor は、Authorization のヘッダから主体を確かめ、確かめられなければ「認証されていない」を返す。トークンの検証は外部の境界のポート（`TokenVerifier`）に任せ、認証の interceptor がそれを所有する。認可の interceptor は、手続き（Procedure）ごとの方針の表で主体をこのサービスの操作の主体へ一度だけ解決して ctx に載せ、表に無い手続きは拒む。書き忘れに気付けるからである。usecase とリポジトリに「本人か」を解決するメソッドを置かない。頻度の制限は、どの入口にいくつ置くかを品質要求の資料が決める。Connect を通らない入口には、同じ役割の HTTP の middleware を置く。

## 組み立てと起動

`main` は、シグナルを ctx に変え、logger を作り、`run(ctx, logger)` を呼び、結果を一度だけ記録して終了コードを決める。`os.Exit` は `defer` を実行しないので、`main` に `defer` を書かない。`run` は、環境で変わるもの（書き込みの pool、読み取り専用の pool、logger、時計、採番器、外部の境界の実装）を作り、組み立ての関数（`NewMux(Deps)`）へ渡す。設定は名前付きの型で読み込み、欠けていれば起動しない。起動のときの依存先のエラーも翻訳してから返す。

組み立ての関数は、`Deps` から、トランザクションの管理、リポジトリ、Query の実装、usecase、handler、interceptor の列を内側から外側へ組み、本番の `run` とテストが同じ関数を呼ぶ。常駐するワーカーは見張りの関数で起動して `run` が返る前に終わりを待つ。停止では、HTTP のサーバーを取り消されていない別の期限付きの ctx で止め、ワーカーが止まってから pool を閉じる。

## テスト：本番の組み立てを通す API のテスト

API のテストは、`NewMux` で handler を組み、`httptest.NewServer` に載せ、生成したクライアントから公開の API として叩く。handler の構造体のメソッドを直接呼ぶテストは書かない。差し替えるのは、トークンを検証するポート、時計、採番器だけで、認証と認可の interceptor は本物を通す。主体は、mock が知っているトークンを Authorization のヘッダに載せて決め、主体の無い要求と他人の要求もヘッダで作る。前提は持ち主の書き込み経路で作る。

確かめるのは、その RPC が持つ公開の結果をひととおりである。成功では、応答の中身と、代表的な一つのテーブルへの反映を見る。その RPC が返しうる分類ごとに、応答の Code と公開の文言が応答の表と具体エラーの文言どおりであることを見る。同じ Code でも文言を決める具体エラーが違う経路は、別のケースにする。回復不能と分類不能は、固定の文言だけが返ることを見る。主体の無い要求が「認証されていない」に、方針の表が求める主体でない要求が拒まれることを見る。欠けた値や形の違う値が「入力が不正」になることを見る。入口のテストが主に担う BDD は、認証、認可、応答の Code、入口での変換を観測するもの（他人の利用者カードでは借りられない）で、ほかの層が主に担う場面を公開の API から見るケースは生成した id を使う。業務の境界、行の全列、トランザクションの境界、ログは確かめない。

## 止まるとき

usecase に無い入力や出力が要るとき、入口で業務の判断や本人の確認が要ると感じたとき、どの RPC に頻度の制限や認可の方針を置くかが資料に無いとき、組み立ての関数が無く本番と同じ組み立てを呼べないとき、interceptor を差し替えないとテストが書けないときは、書かずに持ち主か資料へ返す。報告には、入口と呼ぶ usecase、変換と時刻と主体の出どころ、方針の表への追加、組み立ての変更、確かめた公開の結果、テストが主に担う BDD の ID を書く。
