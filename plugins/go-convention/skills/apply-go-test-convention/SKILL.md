# apply-go-test-convention

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

Go のテストを、どの層でも同じ形で書く。読み終えると、テストの形（表、識別、Given、Then）、資料の BDD の写し方、差し替えてよい境界、テストデータの作り方、実 DB の使い方を、一つの答えに揃えられる。

この規約が守るものは三つである。一つは、**テストが本番の組み立てを通る**ことである。内部の部品を差し替えると、組み立ての誤りをテストが見逃す。二つ目は、**失敗したテストを同じ値で再現できる**ことである。三つ目は、**資料の一つの BDD を、一つのテストだけが名乗る**ことである。同じ BDD を二か所が名乗ると、一つの失敗を二か所が主張し、どちらかが重なりになる。

層ごとに何をテストするか（厚みと責務）は、層別のテストの規約が決める。

## 入力

対象のテストファイル（または書く対象のメソッドと関数）と、写す BDD を持つ資料（業務知識、データモデル）を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約は、対象 repository の AGENTS.md / CLAUDE.md と `references` で渡される。

前提は Go 1.27、testify（`github.com/stretchr/testify`）、`go.uber.org/mock`、`github.com/ory/dockertest/v4` である。

テストを書く場面は二つあり、どちらも通常である。実装が先にある場面では、対象の公開 API を読んで書く。テストが先の場面では、層別の規約と資料から名前とシグネチャを決めて同じ形で書き、コンパイルエラーで赤になる状態を正とする。

## 判断基準

### 形を一つに揃える

対象一つにつきテスト関数は一つで、`{pkg}_test` の外部テストパッケージに置き、公開 API だけを叩く（[単位と命名](references/unit-and-naming.md)）。無名 struct のスライスに、識別、Given、When、Then の順でフィールドを並べ、実行と検証はループ本体に一回だけ書く（[テーブルの形](references/table.md)）。Given は既定でデータにし、`setup` は値で書けない Given がケースごとに違うときだけ置く（[Given](references/given.md)）。Then は `want*` と、分類を土台にした具体エラーの `wantErr` で書く（[Then](references/then.md)）。完全な例は [例](references/examples.md) にあり、書き始める前に一度読む。

### ケースは id / name / description で識別し、BDD は主に担うテストだけが名乗る

ケースは `id`、`name`、`description` で識別する。資料の BDD を写すケースは、資料の ID、見出し、gherkin をそのまま写す。資料の一つの BDD を `id` に写すのは、repository 全体で、その BDD を最も内側で観測できるテストのちょうど一つだけである。写すテストファイルは、どの資料の BDD かを一つだけ宣言する。どのテストも担わない BDD だけを、理由付きで列挙する。詳しくは [ケースの識別](references/case-identity.md) を読む。

### 差し替えてよいのは三つだけ

テストで差し替えてよいのは、制御できない外部の境界、時計、採番の三つだけである。差し替えには、ポートの interface から生成した gomock を使う。それ以外は本番の組み立ての関数で実物を使う。詳しくは [差し替えてよい境界](references/doubles.md) を読む。

### テストデータは決定的に、前提は持ち主の書き込み経路で

テストデータは Builder で作り、既定値は資料の BDD の代表値を固定の値にする。保存済みの前提は、持ち主のコマンドと書き込み経路を順に通して作る。行を直接入れてよいのは、保存済みの破損を検出するテストと、別の配備単位が所有していてコンパイル上 import できない行だけである。詳しくは [テストデータ](references/test-data.md) を読む。

### 実 DB は実物を、試行ごとの期限付きで待つ

実 DB を使うテストは、dockertest で起動した PostgreSQL の実物を使い、起動待ちの各試行に全体より短い期限を付ける。詳しくは [実 DB](references/real-database.md) を読む。

## 手順

1. **対象を一つに決める。** `references` があれば先に読む。一つのメソッドか一つの関数を決める。同じ対象のテスト関数が既にあるなら、そのテーブルにケースを足す。既存のテストが規約に反するなら、ケースを足す前に形を直す。
2. **写す BDD と、主に担うかを決める。** 資料の BDD のうち、この対象が主に担うものを決める。ほかのレベルが主に担う BDD の場面を通すなら、生成した id を使う。
3. **テーブルの型を決める。** Given の形（データ、`setup`、操作列）を決め、差し替えてよい境界だけを mock にし、前提データの作り方を決める。
4. **ケースを書く。** 主に担う BDD を資料の順に写し、資料に無いケースを生成した id でその後ろに足す。どのテストも担わない BDD があれば、列挙する。
5. **ループ本体を一回書く。** 実行と検証を `t.Run` の中に一回だけ書く。
6. **機械検査を通す。** テストが先の場面では、`go vet` と `go test` は対象の未実装のコンパイルエラーで失敗する。これは赤であり停止ではない。失敗の理由が未実装であることを確かめ、形の検査だけを通す。
   ```bash
   go vet ./...
   go test -shuffle=on -count=1 ./...
   go test -count=1 -run 'TestX/BDD-001_' ./...
   python3 scripts/check-cases.py <テストのあるディレクトリ>
   python3 scripts/check-bdd-coverage.py <repository root> <資料.md>...
   ```
7. **報告する。** 出力の項目を返す。

二つの tool は、この `SKILL.md` があるディレクトリの `scripts/` にある。`check-cases.py` は、引数のディレクトリの `*_test.go` の形を検査する。`check-bdd-coverage.py` は、repository root 配下の全 `*_test.go` と、引数の資料（repository root からの相対 path か絶対 path）を突き合わせる。どちらも、違反があれば一行ずつ stdout に出して終了コード 1、入力が無ければ stderr に理由を出して終了コード 2、違反が無ければ終了コード 0 を返す。違反が出たら、ケースを直してから再実行する。

## 停止条件

対象がプライベートで公開 API から観測できないときは、書かない。公開 API から観測できる設計へ戻すことを提案する。対象が `Fuzz*` や `Example*` なら、表の形にならないので対象外として返す。内部の部品を差し替えないと書けないときは、書かずに、ポートの切り方か本番の組み立ての関数の不足を返す。前提データを持ち主の書き込み経路で作れず、二つの例外にも当たらないときは、書かずに、書き込み経路の不足を返す。`go.mod` に testify か `go.uber.org/mock` が無ければ、追加を提案して止まる。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

ケースの名前、`description` の粒度、並びの揺れでは止まらない。資料の BDD の順と語に最も近い形を採り、報告に示して進む。

## 出力

対象とテスト関数の名前、テーブルの型とその理由、ケースの数と内訳（主に担う BDD の ID、資料に無いケース、どのテストも担わない BDD と理由）、差し替えた境界、前提データの作り方（行を直接入れたなら例外のどちらか）、機械検査の結果、層別の規約へ返した論点を報告する。

機械検査が通って言えるのは、次のことだけである。`check-cases.py` は、package が `{pkg}_test` であること、ケースの `id` と `name` がディレクトリの中で一意であること、`id` / `name` / `description` がこの順に並ぶこと、`description` の Given / When / Then の形を判定する。`check-bdd-coverage.py` は、資料の各 BDD が、その資料を宣言したテストの `id:` か列挙に、repository 全体でちょうど一回現れることを判定する。どのテストが主に担うべきかの判断、差し替えが三つの境界だけであること、前提データの作り方が正しいかは、対象を読んで報告する。
