# apply-go-test-convention

[工程順序の定義](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と参照資料を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

これは、**Go のテストコードの「形」を一つに揃える規約**である。どの層のテストでも同じ形で読める。

これは、**何をテストすべきか**を決めるものではない。層ごとの厚みと責務、前提データの作り方（復元・実 DB・投入関数）、テスト支援パッケージの名前と置き場、プロセス単位の共有資源、どの資料のどの BDD をどの package が対象にするかは、この規約の上に載る層別の規約が決める。この規約は形（表・識別・Given・Then）と、資料の BDD を写す位置（`id` / `name` / `description` / 末尾コメント）だけを定義する。

前提: Go 1.27・testify（`github.com/stretchr/testify`）。

テストを書く場面は 2 つあり、どちらも通常である。**実装が先にある**場面では、対象のメソッド・関数を読んで書く。**テストが先**（対象がまだ無い）場面では、層別の規約と資料から対象の名前・シグネチャ・sentinel を決めて同じ形で書き、コンパイルエラーまたは未定義シンボルで赤になる状態を正とする。この規約の形（表・識別・Given・Then）と `check-cases.py` の検査はコンパイルを要しないので、テストが先でもそのまま適用する。

## 入力

- 対象のテストfile（または書く対象のメソッド・関数）と、資料のBDD（ID・見出し・gherkin）。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

## 規約

| # | 柱 | 一言で | 基準資料 |
|---|---|---|---|
| 1 | 単位と命名 | 対象1つにつきテスト関数は1つ。`{pkg}_test`。プライベートはテストしない | [unit-and-naming.md](references/unit-and-naming.md) |
| 2 | テーブルの形 | 無名 struct のスライス。入力と期待値はフィールド、検証はループ本体に1回 | [table.md](references/table.md) |
| 3 | ケースの識別 | `id` / `name` / `description`。資料にあるケースは資料の ID・見出し・gherkin をそのまま写し、無いケースは生成した id。`id` はディレクトリ内で一意・不変。テストしない BDD は末尾コメント | [case-identity.md](references/case-identity.md) |
| 4 | Given | 既定はデータ。`setup` は値で書けない Given がケースごとに違うときだけ。ケース間依存は作らない。入力が引数ではなく、それまでの操作である型は操作列 | [given.md](references/given.md) |
| 5 | Then | `want*` と `wantErr error`（sentinel）。`verify` は等値で書けない性質にだけ追加で。`require` は前提、`assert` は独立した期待 | [then.md](references/then.md) |

規約を満たした完全な例は [examples.md](references/examples.md)。**書き始める前に一度読み、この形を写す。**

## 手順

1. **対象を1つに決める。** `references` があれば先に読む。1つのメソッドか1つの関数（まだ無ければ、層別の規約と資料から決めた名前）。既に同じ対象のテスト関数があるなら、新しく作らずそのテーブルにケースを足す。既存のテストが規約に反する（関数が割れている・`id` が無い等）なら、ケースを足す前に形を直す。`id` が無いケースは、資料に対応するなら資料の ID を、無ければ生成した id を付ける。完了条件: テスト関数名が `Test{型}_{メソッド}` または `Test{関数}` で一意に決まっている
2. **テーブルの型を決める。** Given の形（データ / `setup`）をテスト関数単位で決め、入力が引数ではなく、それまでの操作である型なら `given []op` + `steps []step` を足す。完了条件: フィールドが識別 → Given → When → Then の順に並び、どれがどれかを指せる
3. **ケースを書く。** 層別の規約が指した資料の BDD を、資料の順に `id`（資料の ID）/ `name`（見出し文）/ `description`（gherkin ブロックの転記）へ写し、資料に無いケースを生成した id でその後ろに足す。資料にあるがテストしない BDD は、ファイル末尾に `// テストしない BDD:` と ID・理由を列挙する。完了条件: `description` の各行からフィールドの値が説明でき、対象の資料の ID が全部 `id:` か末尾コメントに現れる
4. **ループ本体を1回書く。** 実行と検証を `t.Run` の中に1回。完了条件: ケースを選り分ける分岐が無い
5. **機械検査を通す。** テストが先の場面では、`go vet` と `go test` は対象未実装のコンパイルエラーで失敗する。これは赤であり停止ではない。失敗理由が対象未実装であることを確かめ、`check-cases.py` だけを通し、`go test` の緑は実装後に確かめる。`scripts/check-cases.py` はこの `SKILL.md` があるディレクトリ直下の tool で、引数はテストのあるディレクトリ。違反があれば違反箇所を 1 行ずつ stdout に出して終了コード 1、`*_test.go` が無ければ stderr に理由を出して終了コード 2、違反が無ければ `違反なし` と終了コード 0。違反が出たらケースを直してから再実行する
   ```bash
   go vet ./...
   go test -shuffle=on -count=1 ./...
   go test -count=1 -run 'TestX/BDD-001_' ./...   # 足したケースを1つずつ単独で。id の後の区切り _ まで書く
   python3 scripts/check-cases.py <テストのあるディレクトリ>
   ```
6. **報告する。** 対象とテスト関数名、テーブルの型（データ / `setup` / 操作列）とその理由、ケース数と内訳（資料にあるケース / 資料に無いケース / テストしない BDD とその理由）、`verify` を使ったなら `want` で書けなかった理由、層別の規約へ返した論点

## 停止条件

止まるのは、資料または規約の契約に反する要求、正式な定義に無い決定が要る、利用者の許可が要る、toolが失敗した、のどれかに当たるときで、それ以外の判断の揺れでは止まらない。欠けているのが業務事実（操作・状態・拒む理由・資料が未決と明示した値）なら止まり、命名・分割・定義場所・並び・テストの置き場のような設計判断の揺れなら仮説を明示して進む。

- 対象がプライベートで公開 API から観測できない → 書かない。公開 API から観測できる設計へ戻すことを提案して止まる
- 対象が `Fuzz*` / `Example*` → 表の形にならない。対象外として返す
- 操作列が一つの業務結果として説明できず、複数の独立した開始条件・結果を含む → 件数では分けず、各ケースが一つの業務結果を観測する境界へ戻してから書く
- `go.mod` に testify が無い → `go get github.com/stretchr/testify` を提案して止まる

止まるときは、書いた範囲と書かなかった範囲を分け、返す先（資料、実装の規約、利用者）と必要な決定を報告に示す。

判断の揺れでは、その時点の根拠から最も筋の良い形を仮説として採り、仮説であることと採らなかった形を報告に明示して進む。

- ケース名、`description`の粒度、テーブルの並びが規約から一意に決まらない: 資料のBDDの順と語に最も近い形を採り、報告に示す。
- 資料のgherkinブロックをそのまま`description`にすると、フィールドに写せない行がある（別の集約・別の層の観測）: `description`を削らず、写せる行でテストを書き、写せない行を検証する層を最も筋の良い仮説として報告に書いて層別の規約へ渡す論点にする。

## 機械検査で言えること

| 検査 | 通ったら言えること |
|---|---|
| `go vet` / コンパイル | 形の違反は見つからなかった |
| `go test -shuffle=on` | テスト関数間の順序依存は見つからなかった（サブテストの順序は変えない） |
| `go test -run 'TestX/BDD-001_'` が通る | そのケースは単独で通る |
| `check-cases.py` | 次の5つの述語が成り立った。1. package 行が `{pkg}_test` である 2. `func Test*`（`TestMain` を除く）ごとに、`id:` 行が1つ以上あり、値は空でなく、同じディレクトリの `*_test.go` 全体で重複しない 3. `id:` / `name:` / `description:` は各1行で始まり、この順に隣接する 4. `name:` の値が同じディレクトリの `*_test.go` 全体で重複しない 5. `description:` は raw string で、`Given:` / `When:` / `Then:` を行頭にこの順で各1回持ち、`And:` は行頭または字下げで `Given:` か `Then:`（またはその `And:`）の後にだけ現れ、`NOTE:` で始まる行とそれに続く字下げ行は無視する。内容が正しいとは言えない |

「テーブル駆動である」「良いテストである」「資料の ID が全部現れる」は、この検査では言えない。資料との突き合わせは資料を読む層別の規約の検査が行い、残りは下のチェックリストを人が読む。

## チェックリスト（機械で言えないことだけ）

- [ ] 対象1つにテスト関数1つ。サフィックス付きの2つ目が無い
- [ ] プライベートを呼んでいない
- [ ] ファイルスコープに `Test*` / `Benchmark*` 以外を定義していない（層別の規約が足す `main_test.go` を除く）。表を支える型はテスト関数の中にあり、表の前に関数が無い
- [ ] フィールドは識別 → Given → When → Then の順。禁止名を使っていない
- [ ] 資料にあるケースの `id` / `name` / `description` は資料の ID・見出し文・gherkin ブロックと一致し、言い換えていない
- [ ] 資料に無いケースの `id` は資料の ID と紛れない生成した id で、`name` は業務語の1文。`description` の各行からフィールドの値が説明できる
- [ ] 資料にあるがテストしない BDD が末尾コメントに理由付きで列挙され、対象の資料の ID が `id:` か末尾コメントのどちらかに全部ある
- [ ] `setup` はケースごとに違うときだけ置き、置いたら全ケースが持ち、資源の取得だけをしている
- [ ] ケース間に依存が無い。`t.Parallel()` はテスト関数の先頭とサブテストの先頭の両方にあるか、両方に無い
- [ ] `wantErr` は sentinel `error`。`bool` や文言部分一致ではない
- [ ] ループ本体に検証が1回。`verify` は追加であって置き換えではない

## 報告

- 対象とテスト関数名、テーブルの型（データ / `setup` / 操作列）とその理由
- ケース数と内訳: 資料にあるケース（ID の一覧）/ 資料に無いケース / テストしない BDD（ID と理由）
- `verify` を使ったケースと、`want` で書けなかった理由
- 機械検査の結果（`go vet` / `go test -shuffle=on` / 単独実行 / `check-cases.py`）
- 層別の規約へ返した論点（写せなかった gherkin の行、対象外にした BDD）
