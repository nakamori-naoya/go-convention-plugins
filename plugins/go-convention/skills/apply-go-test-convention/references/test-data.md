# テストデータ

# Builder で作る

テストの前提となる値オブジェクト、集約、保存済みの行は、テスト支援の Builder で作る。`*_test.go` の中で `New*` を並べて前提を組み立てない。例外は、その `New*` 自体を確かめる生成関数のテストである。

Builder は `New<型名>Builder()` → `With<項目>(...)` → `Build(t)` の形にする。`t` は `Build` でだけ受け取り、コンストラクタでも内部でも持たない。`Build` は先頭で `t.Helper()` を呼び、失敗は `require` で止める。こうすると、Builder はテストの外では使えない。保存済みの行を作る Builder は、`Build(ctx, t)` とする。

```go
lentOn := domainbuilders.NewLentOnBuilder().Build(t)
user := idbuilders.NewUserNoBuilder().WithValue(userU0002).Build(t)
```

Builder が値を作る関数は `Build` だけにする。`MustBuild`、引数の無い `Build`、`Build<状態名>`、作った値を返す getter、Builder を包んで値を返す一行の関数は作らない。状態の作り分けは、状態ごとの Builder の型にする。`With` は `*Builder` を返す。

Builder は、それが組み立てる実装の直下のテスト専用のディレクトリ `builders/`（package 名は `builders`）に置く。呼び手は import の別名（`domainbuilders`、`idbuilders`）で区別する。集約ごとの雑多なテスト支援の package（`<集約名>test`）は作らない。本番のコードは、Builder と mock の package を import しない。

# 既定値は決定的にする

Builder の既定値は、資料の BDD で使う代表値を固定の値にする（利用者番号 `U-0001`、貸出日 2026年10月1日）。乱数、現在時刻、採番を既定値にしない。失敗したテストを、同じ値で再現できるようにするためである。識別子は `With` で差し替えられるようにする。

同じ package で意味を持つ固定値（利用者番号、UUID）を何度も使うなら、ファイルスコープの `const` に名前を付けて置き、文字列を繰り返さない。`description` は読み物なので、`const` を連結せず、場面の文章をそのまま書く。

乱数を使うテスト（プロパティベースのテストなど）は、種を固定するか、失敗のときに種を出力する。

# 対象そのものは Builder で作らない

テストの対象そのものは、Builder で作らない。値オブジェクトのテストではその値オブジェクトの `New*` を直接呼ぶ。集約のテストでは初期状態の型と `Restore*` を直接組む。リポジトリのテストでは、そのリポジトリの `Apply*` を直接呼ぶ。Builder を使うのは、対象の外側にある前提（別の値オブジェクト、別の集約、上流の保存済みの状態）を作るときだけである。対象を Builder で作ると、Builder の中の誤りと対象の誤りが打ち消し合う。

# 保存済みの前提は、持ち主の書き込み経路で作る

保存済みの前提は、そのデータの持ち主のコマンドと書き込み経路を、順に通して作る。「延滞の貸出がある利用者」という前提なら、本を借りる → `ApplyLent` → 延滞にする → `ApplyOverdue` を、実物の集約と実物のリポジトリで順に通す。Builder が作るのは、コマンドへ渡す入力（利用者番号、資料番号、貸出日）だけである。`Restore*` で延滞の貸出を直接組んだり、表に行を直接入れたりしない。集約の不変条件を破った前提を、テストが黙って作れてしまうからである。

保存済みの前提を作る Builder は、ctx のトランザクションに乗らない。自分でトランザクションを張って確定させてから返す。前提は、テストの対象を呼ぶ前に確定しているべきだからである。

例外は二つだけである。

**保存済みの破損を検出するテスト。** 集約からは作れない保存済みの破損（値オブジェクトが拒む値が保存されている）を検出するテストでは、目的を名前にした最小の行を直接入れる。

**別の配備単位が所有する行。** 前提の行を所有するのが別の配備単位（別のプロセスの集約）で、Go の `internal` の規則か module の境界のために、テストの package から持ち主の書き込み経路をコンパイル上 import できない場合である。lint や配置の好みで import していないだけなら、この例外に当たらない。このときは、その行を上流の契約として扱い、上流の状態の名前を付けた Builder を一つ置く。入れる行は推測で組まず、データモデルの資料の BDD にある After の行を写す。行を直接入れる理由は、その Builder の型のコメントに一度だけ書く。

直接入れる行を読み書きするテスト専用の SQL は、本番の SQL と別の生成の package に置き、本番のコードからは import しない（置き場は永続化層のテストの規約が決める）。
