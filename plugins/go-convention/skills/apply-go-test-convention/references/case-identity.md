# ケースの識別

一つのケースは、`id` で指せて、`name` で呼べて、`description` で説明できる。三つとも必須で、この順に置く。三つの値は、資料（業務知識、データモデル）に BDD があるならその資料から写し、無いなら自分で書く。

# id

資料の BDD を写すケースは、資料の ID をそのまま `id` にする（`BDD-003`）。書き換えも付け替えもしない。資料の ID がテストの `id` なら、資料とテストを機械で突き合わせられ、`-run` で一つのケースを指せる。

```go
			id:   "BDD-003",
			name: "5冊借りている利用者は6冊目を借りられない",
			description: `Given: 利用者 U-0001 は貸出中の本を5冊借りており、延滞の貸出は無い
When: 利用者 U-0001 が2026年10月1日 10:00に本を借りる
Then: 貸出は生まれない
  NOTE: Rule: 貸出上限に達している利用者が本を借りる
    Reason: 一人の貸出中と延滞の貸出は5冊を超えない`,
```

資料に無いケースは、生成した id を使う（`7c2e19`）。生成の方法と書式は決めない。資料に無いケースに資料風の番号を付けると、資料にある ID と区別がつかなくなる。連番にすると、採番が中央の管理になる。

```go
			id:   "7c2e19",
			name: "4冊借りている利用者は5冊目を借りられる",
			description: `Given: 利用者は貸出中の本を4冊借りており、延滞の貸出は無い
When: 利用者が2026年10月1日 10:00に本を借りる
Then: 貸出中の貸出が生まれ、返却期限は2026年10月15日である`,
```

`id` は、同じディレクトリ（Go の package）の `*_test.go` 全体で一意にする。振り直さず、消した id を使い直さない。`id` は、レビューや失敗のログの中で「あのケース」を指すものだからである。`name` は変えたくなる文で、`t.Run` の位置は並べ替えで変わるので、変わらないものが一つ要る。それが `id` である。

# name

資料の BDD を写すケースは、資料の見出しの文（ID を除いた部分）をそのまま `name` にする。資料に無いケースは、業務の言葉の一文にする（「〜すると〜になる」「〜は〜できない」）。技術の語（`nil`、`panic`、関数の名前）を入れず、要るなら `description` に書く。`name` は、同じディレクトリの `*_test.go` 全体で重複させない。重複するなら、二つのケースは同じか、`name` が粗い。

# description

`description` は raw string で書き、`Given:`、`When:`、`Then:` を行頭に、この順で、一回ずつ置く。`And:` は、`Given:` か `Then:` に続けて、空白二つで字下げして置き、続けてよい。`When:` の後には置かない。`When:` は一行にする。拒むケースは、`Then:`（またはその `And:`）の後に、空白二つで字下げして `NOTE:` を置き、規則と理由を書く。続く行（`Reason:`）はさらに字下げする。機械の検査は、`NOTE:` とそれに続く字下げの行を読まない。

資料の BDD を写すケースは、資料の gherkin のブロックを、字下げと `NOTE:` を含めて改変せずに写す。言い換えず、省かず、行を足さない。資料に無いケースは、同じ形で業務の言葉で書き、読んだ人がフィールドの値（入力と期待）を組み立て直せるようにする。

縦に分けて書くのは、表のフィールドと一対一で目を往復するためである。`Given:` の行は Given のフィールドに、`When:` の行は引数の名前のフィールドに、`Then:` の行は `want*` と `wantErr` に対応する。`description` に書いてあるのにフィールドに無い（またはその逆）なら、どちらかが嘘をついている。資料を写したケースで、フィールドに写せない行があるなら、それは `description` を削る理由ではない。その行を主に担う別のレベルのテストがある、ということである。

# 資料の BDD を名乗るのは、主に担うテストだけ

資料の一つの BDD を `id` に写すのは、repository 全体でちょうど一つのケースだけである。写すのは、その BDD の `Then:` を最も内側で観測できるテスト（主に担うテスト）である。どのレベルを主担当にするかの原則（より小さく決定的な境界を主担当にする）は testing-strategy が持つ。その原則を Go の層へ当てると、次のようになる。集約のコマンドが受けるか拒むか、次の状態、発するイベント、値オブジェクトの条件を観測する BDD は、ドメインのテストが主に担う。保存される行の形と、DB の制約が守る拒否を観測する BDD は、永続化層のテストが主に担う。複数の書き込みが同じ確定で起きることと手順の順序は、usecase のテストが主に担う。認証、認可、応答の Code、入口での変換は、handler のテストが主に担う。

同じ場面を別のレベルのテストが通っても、そのケースは生成した id を使い、資料の ID を名乗らない。二つのテストが同じ BDD を名乗ると、一つの失敗を二か所が主張し、どちらかが重なりになる。

資料の ID を写すテストファイルは、どの資料の BDD かを、ファイルスコープのコメントで一つだけ宣言する。資料の ID は資料の中でだけ一意なので、資料の path と組にして初めて一つの BDD を指せるからである。path は repository の root からの相対 path にする。

```text
package domain_test

// BDD の資料: docs/lending/業務知識.md
```

一つのテストファイルが宣言する資料は一つだけである。二つの資料の BDD を写すなら、テストファイルを分ける。

# どのテストも担わない BDD

資料の BDD のうち、どのレベルのテストも担わないものだけを、その BDD を最も担いそうなレベルのテストファイルの末尾に、`// どのテストも担わない BDD:` に続けて、ID と理由を一行ずつ列挙する。そのファイルも、同じ資料を宣言する。

```text
// どのテストも担わない BDD:
// BDD-006 本人の確認は認証の外部サービスが行い、このサービスのどのテストでも再現しない
```

列挙するのは、repository のどのテストの `id:` にも現れない BDD だけである。「この package ではテストしない」を層ごとに並べると、同じ BDD が層の数だけ列挙され、どれが本当に担われていないのかが読めなくなるからである。

理由は一行で、なぜどのテストでも再現しないかを書く。後で読む人が、書き忘れと判断の結果を区別できるようにするためである。列挙は一ファイルに一つ、ファイルの最後に置く。置き場が一つなら、探す場所も一つで済む。

# 機械で見られること

`scripts/check-cases.py` が判定する述語は [SKILL.md](../SKILL.md) の「機械検査で言えること」にある。資料の各 BDD が、repository 全体でちょうど一回、主に担うテストの `id:` か列挙に現れることは、`scripts/check-bdd-coverage.py` が判定する。BDD ID の文法と一意の範囲は、資料を作る側（業務知識とデータモデルの資料）が決める。この検査は、資料の `### [ID] 見出し` から ID を読むだけである。
