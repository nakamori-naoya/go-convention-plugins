# ケースの識別

1ケースは **`id` で指せて、`name` で呼べて、`description` で説明できる**。3つとも必須で、この順に置く。3つの値は、資料（BDD を持つ業務知識・ドメインモデル・データモデルの資料）にケースがあるならその資料から写し、無いなら自分で書く。

| | 資料にあるケース | 資料に無いケース |
|---|---|---|
| `id` | 資料の ID そのもの（`BDD-014`） | 生成した id |
| `name` | 資料の見出し文そのもの | 業務の言葉で1文 |
| `description` | 資料の gherkin ブロックを改変せず転記 | 同じ形で自分で書く |

## 1. `id`

```go
			id:   "a3f9c1",
```

| 規則 | 内容 | 理由 |
|---|---|---|
| 資料にある | 資料の ID をそのまま使う（`BDD-014`）。書き換えない・付け替えない | 資料の ID がテストの `id` なら、資料とテストを機械で突き合わせられる。「資料の BDD がテストにあるか」が `-run` と grep で言える |
| 資料に無い | 生成した id を使う。生成方法と書式は規約で決めない。例の `a3f9c1` は生成した id の一例 | 資料に無いケースに資料風の番号を付けると、資料にある ID と区別がつかない。連番にすると採番が中央管理になる |
| 一意の範囲 | 同じディレクトリ（Go の package）の `*_test.go` 全体で一意 | 資料の ID は1つのケースにしか対応しない。同じ ID が2つのテスト関数にあるなら、資料の1シナリオを2か所で検証している |
| 不変 | 振り直さない。消した id を再利用しない | `id` はレビュー・失敗ログの中で「あのケース」を指す。振り直すと過去の言及が別のケースを指す |

`name` は変えたくなる文で、`t.Run` の位置は並べ替えで変わる。**変わらないものが1つ要る**。それが `id` である。

## 2. `name`

```go
			name: "空のスタックからは取り出せない",
```

- 資料にあるケースは、資料の見出し文（`### [BDD-014] 一部でも重なる利用枠の仮押さえは成立しない` の ID を除いた部分）をそのまま使う
- 資料に無いケースは、業務の言葉で1文。「〜すると〜になる」「〜は〜できない」の形。技術語（`nil` / `panic` / 関数名）を入れない。要るなら `description` に書く
- 同じディレクトリの `*_test.go` 全体で重複しない。重複するなら2つのケースは同じか、`name` が粗い

## 3. `description`

```go
			description: `Given: スタックが空である
When: 取り出す
Then: 空のため取り出せないと拒まれる
  And: スタックは空のままである
  NOTE: Rule: 空のスタックからは取り出せない
    Reason: 取り出す値が無く、取り出しの結果を作れないため`,
```

| 規則 | 内容 |
|---|---|
| 書式 | raw string。`Given:` / `When:` / `Then:` を行頭に、この順で、各1回 |
| `And:` | `Given:` / `Then:` に続けて、空白2つで字下げして置く。連続してよい。`When:` の後には置かない |
| `NOTE:` | 拒むケースの規則と理由。`Then:`（またはその `And:`）の後に空白2つで字下げし、続く行（`Reason:` 等）はさらに字下げする。機械検査は `NOTE:` とそれに続く字下げ行を読まない |
| `When:` | 1行。操作列（`steps`）は1行に列挙する |
| 言葉 | 業務の言葉。読んだ人がフィールドの値（入力と期待値）を再構成できること |
| 資料にある | 資料の gherkin ブロックを、字下げと `NOTE:` を含めて改変せず転記する。言い換えない・省かない・行を足さない |

資料 `### [BDD-014] 一部でも重なる利用枠の仮押さえは成立しない` の gherkin ブロックは、次の形で写る（資料の ID・見出し・ブロックがそのまま `id` / `name` / `description` になる）:

```text
		{
			id:   "BDD-014",
			name: "一部でも重なる利用枠の仮押さえは成立しない",
			description: `Given: 予約可能顧客である予約者がいる
  And: 大会議室には2026年9月18日 10:00から11:00までの確定予約がある
When: その予約者が2026年9月18日 10:30から11:30までの大会議室を仮押さえする
Then: その予約者の仮押さえ予約は成立しない
  And: 大会議室の2026年9月18日 10:00から11:00までの確定予約は維持される
  NOTE: Rule: 同じ会議室の重なる利用枠へ、現在有効な予約は一つしか存在しない
    Reason: 10:30から11:00までが既存の確定予約と重なっており、二件目の有効な予約になるため`,
```

縦に分けるのは、表のフィールド（Given のフィールド / When の引数 / Then の `want`）と1対1で目を往復するためである。

| `description` の行 | 対応するフィールド |
|---|---|
| `Given:`（とその `And:`） | `values` / `given` / `seed` / `setup` |
| `When:` | 引数名のフィールド / `steps` |
| `Then:`（とその `And:`） | `want*` / `wantErr` / `verify` |

`description` に書いてあるのにフィールドに無い（または逆）なら、どちらかが嘘をついている。書き終えたら行とフィールドを突き合わせる。資料を転記したケースでフィールドに写せない行があるなら、それは `description` を削る理由ではなく、その行を層別の規約へ返す理由である。

## 4. 資料の BDD を名乗るのは、主に担うテストだけ

資料の一つの BDD を `id` に写すのは、repository 全体でちょうど一つのケースだけである。写すのは、その BDD の `Then:` を最も内側で観測できるテスト（主に担うテスト）である。

| BDD の `Then:` が観測するもの | 主に担うテスト |
|---|---|
| 集約のコマンドが受けるか拒むか、次の状態、発するイベント、値オブジェクトの条件 | ドメインのテスト |
| 保存される行の形、DB の制約が守る拒否 | 永続化層のテスト |
| 複数の書き込みが同じ確定で起きること、手順の順序 | usecase のテスト |
| 認証、認可、応答の Code、入口での変換 | handler のテスト |

同じ場面を別のレベルのテストが通っても、そのケースは生成した id を使い、資料の ID を名乗らない。二つのテストが同じ BDD を名乗ると、一つの失敗を二か所が主張し、どちらかが重なりになる。

資料の ID を写すテストファイルは、どの資料の BDD かを、ファイルスコープのコメントで一つだけ宣言する。資料の ID は資料の中でだけ一意なので、資料の path と組にして初めて一つの BDD を指せるからである。path は repository の root からの相対 path にする。

```text
package domain_test

// BDD の資料: docs/lending/業務知識.md
```

一つのテストファイルが宣言する資料は一つだけである。二つの資料の BDD を写すなら、テストファイルを分ける。

## 5. どのテストも担わない BDD

資料の BDD のうち、どのレベルのテストも担わないものだけを、その BDD を最も担いそうなレベルのテストファイルの末尾に、`// どのテストも担わない BDD:` に続けて、ID と理由を一行ずつ列挙する。そのファイルも、同じ資料を宣言する。

```text
// どのテストも担わない BDD:
// BDD-006 本人の確認は認証の外部サービスが行い、このサービスのどのテストでも再現しない
```

| 規則 | 理由 |
|---|---|
| 列挙するのは、repository のどのテストの `id:` にも現れない BDD だけ | 「この package ではテストしない」を層ごとに並べると、同じ BDD が層の数だけ列挙され、どれが本当に担われていないのかが読めなくなる |
| 理由は一行。なぜどのテストでも再現しないかを書く | 後で読む人が、書き忘れと判断の結果を区別できる |
| 列挙は一ファイルに一つ、ファイルの最後に置く | 置き場が一つなら、探す場所も一つ |

## 6. 機械で見られること

`scripts/check-cases.py` が判定する述語は [SKILL.md](../SKILL.md) の「機械検査で言えること」にある。資料の各 BDD が、repository 全体でちょうど一回、主に担うテストの `id:` か列挙に現れることは、`scripts/check-bdd-coverage.py` が判定する。BDD ID の文法と一意の範囲は、資料を作る側（業務知識とデータモデルの資料）が決める。この検査は、資料の `### [ID] 見出し` から ID を読むだけである。
