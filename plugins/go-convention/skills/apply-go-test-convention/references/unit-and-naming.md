# 単位と命名

対象（一つのメソッド、一つの関数）一つにつき、テスト関数は一つにする。テスト関数が割れると、「どこにケースを足すか」が毎回の判断になり、同じケースが両方に書かれるか、どちらにも書かれなくなる。対象一つ、テスト関数一つ、表一つの対応があるから、「このメソッドのケースは全部ここにある」と言える。どの対象にテストを持つかは層別の規約が決める。

# テスト関数名

メソッドのテスト関数は `Test{型}_{メソッド}`（`TestPendingLoan_Borrow`）、コンストラクタと関数のテスト関数は `Test{関数}`（`TestNewCount`）と名付ける。ベンチマークは `Benchmark{型}_{メソッド}` か `Benchmark{関数}` にする。アンダースコアは、型名とメソッド名の間にだけ置く。

名前に接尾辞を付けない。`_EdgeCases`、`_Error`、`_Complexity` は二つ目のテスト関数であり、置かない。状態ごとに分けた型（`PendingLoan`、`OnLoan`）は別の型なので、それぞれにテスト関数を持つ。`Benchmark*` はケースの表を持たず、対象一つに一つで、入力を固定する。

# パッケージとファイル

パッケージ名は `{pkg}_test`（外部テストパッケージ）にする。実装と同じパッケージにいると非公開のものに手が届くので、届かない場所に置く。ファイル名は `{本体のファイル名}_test.go` にし、対象とテストを一対一で並べる。`helper_test.go` のような任意の名前を作らない。対象のパッケージは通常の import で読み、外から見える API だけを叩く。

# 非公開のものをテストしない

`{pkg}_test` にいる時点で、非公開の関数、メソッド、フィールドには手が届かない。これは制約ではなく目的である。公開 API だけをテストしていれば、内部を丸ごと書き換えても、テストは緑のままでいられる。

内部の関数が複雑で単体で確かめたくなったら、公開 API を通して観測できる振る舞いに言い直す。言い直せないなら、その関数は別のパッケージの公開関数にする。内部の状態を見たくなったら、公開のクエリで観測する。無いなら、型に問い合わせが足りない。`export_test.go` で内部を晒すことはしない。外部テストパッケージにした意味が消えるからである。

# *_test.go に置くもの

ファイルスコープに置くのは、`Test*` と `Benchmark*` と、`const` だけである。表を支える型（`fixture`、`opKind`、`op`、`step` と種別の定数）は、テスト関数の中で宣言する。`{pkg}_test` は一つの名前空間なので、ファイルスコープに型を置くと、二つ目のテスト関数で `fixture` が衝突する。関数の中なら、テスト関数ごとに同じ名前で持てる。

`const` だけは例外にする。同じ package の複数のテストで同じ意味の固定値（利用者番号、UUID）を使うとき、文字列を繰り返さずに名前を付けるためである。`const` は値を変えられず、ケースの間の依存を作らない。`var` は置かない。

テスト関数の中に置く関数は、ループ本体の中の局所クロージャ（操作列を実行する `run` など）だけである。表の前に関数を置かない。表の前に置いた関数はケースから参照され、ファイルスコープのヘルパーと同じものになる。

セットアップ、生成、検証のヘルパー関数や、汎用のアサーション関数は置かない。テストデータは Builder（[テストデータ](test-data.md)）へ、実 DB の基盤は共有のテスト支援 package（[実 DB](real-database.md)）へ出す。パッケージ変数も置かず、資源は `setup` が取得して `t.Cleanup` で返す（[Given](given.md)）。実 DB だけは、`main_test.go` の共有の基盤が持つ。`TestMain` は、実 DB を使う package だけが、`main_test.go` に一つ置く（[実 DB](real-database.md)）。他のファイルには置かない。
