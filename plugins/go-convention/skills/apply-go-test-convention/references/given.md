# Given の置き方

Given は、既定では宣言的なデータとして表に書く。`setup func` は、値として表に書けない Given がケースごとに違うときだけの逃げ道である。ケースの間に依存を作らない。入力が引数ではなく、それまでの操作である型は、操作列で表す。

# 既定はデータ

Given のフィールドは、`description` の `Given:` の行と一対一で対応させる。次の例では、「借りている冊数」と「延滞の貸出の冊数」が、それぞれ一つのフィールドになっている。

```go
		lent        lending.Count  // Given: 借りている冊数
		overdue     lending.Count  // Given: 延滞の貸出の冊数
```

データから SUT を組み立てるコードは、ループ本体に一回だけ書く。

```go
			pending := lending.NewPendingLoan(lending.NewStanding(tt.lent, tt.overdue))
```

表を縦に読んでケースの差分が分かるのは、Given がデータのときだけである。Given の値が値オブジェクトで、その生成が失敗しうるなら、表の前で一度だけ作り、`require.NoError` で確かめてから表で名前を使う。生成の条件はその値オブジェクトのテストが確かめるので、ここで失敗するなら表以前の問題である。

```go
	// 表で使う冊数。生成の条件は Count のテストが確かめるので、ここで失敗するなら表以前の問題である。
	none, err := lending.NewCount(0)
	require.NoError(t, err)
	one, err := lending.NewCount(1)
	require.NoError(t, err)
	four, err := lending.NewCount(4)
	require.NoError(t, err)
	five, err := lending.NewCount(5)
	require.NoError(t, err)
```

Given の struct が肥大化するなら、それは SUT の引数が多すぎるという合図である。テストではなく、型の設計で直す。

# 逃げ道の setup

`setup func(t *testing.T) fixture` を使ってよいのは、Given に `t` が要る（`t.TempDir`、`t.Cleanup`、トランザクション）か、直列化できない依存（DB のハンドル、チャネル）が要るときだけである。それ以外はデータで書く。

`setup` の戻り型は、テスト関数の中で宣言した `fixture` struct にし、SUT と、Then で覗く共同作業者（保存先のディレクトリなど）を持たせる。SUT だけを返すと、Then で副作用を観測できない。`any` や `map` は型を失うので使わない。

`setup` フィールドを置くのは、ケースごとに `setup` が違うときだけである。置いたら全ケースが持つ。全ケースで同じ `setup` は、フィールドではなく、ループ本体の Given を組み立てるコードである。有無がケースで変わると Given の読み方が変わり、表を縦に読めなくなる。

`setup` がするのは資源の取得だけである。資源に何を入れたかは `seed` などのデータのフィールドに出し、投入はループ本体で行う。そうすれば前提の中身が表に出る。`setup` に入れると、閉じた関数の中に隠れる。`setup` に When と Then を入れない。操作が入った時点で、ケースごとに検証が散る形に戻るからである。

`setup` にはサブテストの `t` を渡す。`t.Cleanup` がサブテストの終わりに走るからである。親の `t` を渡すと、全ケースが終わるまで資源が残る。

# ケースの間の依存と順序

ケースの間に依存を作らない。各ケースが自分の世界を組み立てる。どのケースも、単独で `-run 'TestX/BDD-001_'` を指定して通る。どの順で走っても同じ結果になる。`go test -shuffle=on` はテスト関数の間の順序だけを入れ替え、サブテストの順序は変えない。落ちれば、テスト関数の間の依存が確定する。「作成してから取得する」という連続は、二つのケースではなく、一つのケースの操作列（次の節）にする。

並列にできるかどうかは、ケースの属性ではなく、テスト関数（SUT と資源）の属性である。`t.Parallel()` は、テスト関数の先頭とサブテストの先頭の両方に書くか、両方に書かないかのどちらかで、片方だけにはしない。書かないときは、ループの直前のコメントで共有資源を名指しする（`// 同一スキーマの users テーブルを共有するため直列で走らせる。`）。「並列にすると不安定」は隔離が壊れている証拠であり、並列を諦める理由ではなく、隔離を直す理由である。

# 操作列

スタック、キュー、集約のように、入力が引数ではなくそれまでの操作である型は、操作列で表す。表を支える型（`opKind`、`op`、`step`）はテスト関数の中で宣言する。資源が要る型は、`setup` で `fixture` を取得し、`given` と `steps` は `f.sut` を操作する。

準備の操作 `given []op` と、操作とその直後の期待の組 `steps []step` を分ける。`given` は前提で、期待を持たない。`steps` は観測値に期待を持つ。操作の実行は、`switch` を持つ局所クロージャ一つに集め、`given` も `steps` もそこを通す。`given` は `require.NoError` だけで、`steps` は `want` と `wantErr` で検証する。実行が一か所なら、検証も一か所に留まる。

操作ごとに観測値を一つ決め、`step.want` はその値にする。観測値の型は、全操作で一つにする。期待の無い `step` は作らない。積む操作なら積んだ後の個数、取り出す操作なら取り出した値を観測する。型が揃わないなら、`steps` に入れる操作を対象のメソッドだけにし、他の操作は `given` に置く。

最終状態は `want{何}` に置き、公開のクエリで観測できる射影（`wantLen`、`wantIsEmpty`）と突き合わせる。観測できない内部状態を見たくなったら、それは型に問い合わせが足りないということである。不変な SUT は受け直し（`s = s.Push(v)`）、可変なら受け直さない（`s.Push(v)`）。形は同じである。

`steps` は、一つの業務の結果へつながる操作列である。操作の数で切らない。独立した開始条件や、別の業務の結果が混ざるなら、ケースの境界を分ける。同じ結果に要る操作は、順序を保つ。

# 後始末

資源を取得した `setup` の中で、取得の直後に `t.Cleanup` を登録する。`teardown`、`before`、`after` のフィールドは使わない。後始末は「何を作ったか」に従い、ケースには従わないからである。`t` を受け取る取得（`t.TempDir()`）は、取得する側が `t.Cleanup` を登録済みなので、何も書かない。自分で変えた状態（権限、接続、トランザクション）は、変えた直後に `t.Cleanup` で戻す。`t.Cleanup` は後に登録したものから先に走るので、戻す処理を後に登録すれば、`t.TempDir()` の削除より先に走る。

`t.Cleanup` は `require` の `FailNow` でも走り、サブテストの `t` に紐づくので、並列とも整合する。
