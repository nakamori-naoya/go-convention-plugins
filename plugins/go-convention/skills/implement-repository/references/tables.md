# テーブルの型の写し方

データモデルの資料と物理設計の資料が、テーブルの型、名前、列、制約を決める（W1 が持ち主）。リポジトリは、それをそのまま写す。テーブルの型を実装の側で変えたり、列を足したりしない。資料と実装が食い違ったら、資料の持ち主へ返す。

# 業務のイベント列（戦術的 DDD の集約）

集約の出来事を積むイベント列の型は、次の三つのテーブルで表される。物理設計が、派生のテーブルを足すこともある。

**リソースのテーブル**（例：`loans`）は、集約が生まれたときに決まる事実を持つ。生成のイベントの `Apply` が一行を追加する。リソースの現在の状態と版は、楽観ロックと業務の読み取りのために、列（`status`、`current_version`）として持つことが許されている（利用者の裁定）。資料がそれを持たせたなら、状態を変える `Apply` は、イベントの追加と同じトランザクションで、読んだ版を条件にその列を更新する。更新した行が0件なら、先に別の操作が版を進めたので「同時更新で競合した」を返す。原則として持たないのは、加工した情報（集計、件数、平均、順位）だけである。

**基底イベントのテーブル**（`<対象>_base_events`、例：`loan_base_events`）は、出来事に共通の事実を持つ。リソースの識別子を外部キーで持ち、イベントの種類、集約の中の版、出来事が起きた時点（`occurred_at`、この一列だけ）を持つ。`Apply<イベント名>` は、どれも一行を追加する。

**詳細イベントのテーブル**（`<対象>_<過去分詞>_events`、例：`loan_lent_events`、`loan_marked_overdue_events`）は、その出来事に固有の、業務が与えた値を持つ。主キーは基底イベントの識別子で、外部キーを兼ねる。リソースの識別子を重ねて持たない。固有の値が無い出来事（`loan_returned_events`）も、表を置き、一行を追加する。

**派生のテーブル**は、物理設計が、制約と読み取りを支えるために置く導いた値である（リソースの列で足りないときに置く）。一次データは基底イベントと詳細イベントで、`Apply` は、イベントを追加するのと同じトランザクションで派生のテーブルを更新する。片方だけを確定させない。

現在の状態と版をどこに持つか（リソースの列か、派生のテーブルか）は、データモデルと物理設計の資料が決める。リポジトリは、資料が決めた場所を読み書きする。W1 の生成例は、リソースの列に持つ。

# 版

`Apply<イベント名>` は、イベントの版をそのまま基底イベントの `version` に書く。版を決めるのはコマンドで、リポジトリは推測も採番もしない。同じ集約の同じ版は、物理設計の一意制約（`loan_id, version`）が一つに限る。二つの操作が同じ版を読んで書こうとすると、後の一方の違反（SQLSTATE 23505）を、翻訳表で「同時更新で競合した」へ写す。

# 時刻

基底イベントの `occurred_at` は、出来事が起きた時点である。イベントが業務の時刻を持つ（コマンドが業務の時刻を引数で受けた）なら、その値を書き、Clock を読まない。イベントが業務の時刻を持たないなら、`Apply` の中で Clock から一度だけ取り、同じ操作で書くすべての行に同じ値を写す。

# 技術的な処理のライフサイクル

技術的な処理（Outbox の要求、回収、成功、失敗）のテーブルの型も、W1 が決める。図書館の延滞の通知では、要求（`overdue_notice_requested_events`）、回収（`overdue_notice_claimed_events`）、成功（`overdue_notice_succeeded_events`）、失敗（`overdue_notice_failed_events`）の四つである。どれも追加だけで、基底イベントを置かない。

要求は、発生元の集約のイベントの `Apply` が、同じトランザクションで追加する（延滞にする `ApplyOverdue` が、延滞の通知の要求を追加する）。回収、成功、失敗は、単純なパターンの手順のリポジトリ相当の口が追加する（[単純なパターンの口](procedure-store.md)）。

# 制約

物理設計が決めた制約（一意、部分一意、外部キー）を、DDL として写す。値の範囲の CHECK 制約は、ドメインモデルだけが書く業務のテーブルには置かない。値の正しさの持ち主は、ドメインモデルだからである。技術的な処理のテーブルは、ドメインモデルの外の手順が書くので、物理設計が決めた CHECK を置く。

名前付きの一意制約の違反は、翻訳表（`Constraints`）で、資料の拒む理由か「同時更新で競合した」へ写す。対応に無い一意制約の違反と、一意以外の制約の違反は、実装の間違いとして「分類不能」のまま返す（handle-errors の翻訳表）。
