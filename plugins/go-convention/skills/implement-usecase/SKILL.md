# implement-usecase

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

一つの業務イベント、一つの技術的な処理、一つの読み取りを、usecase として書く。読み終えると、どの形で書き、トランザクションをどう張り、何に依存してよいかを決められる。

どの処理をどのパターンで書くか、command の流れ（usecase は判断も材料集めもしない）とその理由、トランザクションの所有は、development-convention の `apply-layer-convention` が決める。この skill が受け持つのは、それを Go の形に写すことだけである。

## 入力

対象の業務イベント（または技術的な処理、読み取り）と、そのパターン（apply-layer-convention が決める）、ドメインの実装か手順が所有する口、物理設計の資料の絶対 path を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

先に赤いテストがある場面も通常である。テストが前提にする型、入力、出力、コンストラクタに合わせ、テストを変えずに緑にする実装を書く。テストが資料に無い協調や、ドメインが持つべき判断を usecase に求めていれば、実装で補わずに返す。

## 判断基準

### 戦術的 DDD の command

流れは `apply-layer-convention` に従い、Go では `Find*` で集約か初期状態の型を得て、コマンドを一回呼び、`<Command>Result` のイベントを `Apply*` に渡す。依存は `tx.Manager`、ドメインの永続化ポート、採番器、外部の境界のポートだけにする。入力は値オブジェクトの struct で受け、識別子はトランザクションの外で採番し、出力は結果のイベントから作る。物理設計の指定は、名前のある `tx.Options` で `tx.Manager.Run` に渡す。詳しくは [command の形](references/command.md) を読む。

### 単純なパターンの手順

その代表は Outbox の回収と発行である。Outbox では、業務の変更と同じトランザクションで送る要求を一行記録しておき、別の手順がその行を回収して外へ送る。リポジトリ相当の口を順に呼ぶ。外部との通信はトランザクションの外に置き、進捗は一件ごとに確定させ、外部への口には冪等の鍵を渡す。一件の失敗で続けるか打ち切るか、一時失敗か恒久失敗かは、handle-errors の処理の表（エラーの分類ごとに、失敗が全体に及ぶか、再処理で通りうるかを決めた表）で決める。詳しくは [手順の形](references/procedure.md) を読む。

### query

読み取りのポートを呼んで読み取りモデルを返し、トランザクションを張らない。詳しくは [query の形](references/query.md) を読む。

## 手順

1. **形を確かめる。** `references` があれば先に読む。対象が command、手順、query のどれかと、apply-layer-convention の判断を確かめる。
2. **入力と出力を決める。** 入力の値オブジェクトと、業務の時刻の有無と、出力を決める。
3. **依存を並べる。** 形ごとに許された依存だけを、コンストラクタの引数にする。
4. **トランザクションを決める。** 物理設計の指定から `tx.Options` を決め、手順ではトランザクションの区切りと外部との通信の位置を決める。
5. **`Execute` を書く。**
6. **機械検査を通す。**
   ```bash
   go build ./... && go vet ./...
   go tool golangci-lint run ./...
   ```
   usecase の package が pgx、sqlc の生成型、connect、proto を import していないことと、command の package が読み取りの package を import していないことを、linter と import の一覧で確かめる。
7. **報告する。** 出力の項目を返す。

## 停止条件

usecase で状態を見て分岐したくなったとき、集約に無いコマンドを呼びたくなったときは、書かずに implement-domain-model と資料へ返す。コマンドが受けない状態の拒む理由が資料に無く、和型に置けていないなら、その usecase を書かない。並行実行の保証が論理データモデルにあるのに物理設計に指定が無ければ、物理設計の資料へ返す。二つの集約を同じ時点で成立させるか別の時点でよいかが資料に無ければ、資料の持ち主へ問う。外部の受け手が冪等を約束できないなら、資料の持ち主へ返す。手順の中で業務の判断が要ると分かったら、apply-layer-convention と資料へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

## 出力

usecase の一覧（名前、形、対応する業務イベントか処理か読み取り）、それぞれの入力と出力と依存、トランザクションの指定と物理設計の根拠、手順ならトランザクションの区切りと外部との通信の位置と冪等の鍵、返した論点、機械検査の結果を報告する。

機械検査が通って言えるのは、ビルド、vet、linter、import の禁止に違反が無いことだけである。usecase が判断していないこと、トランザクションの区切りが正しいことは、test-usecase のテストと、対象を読んで確かめる。
