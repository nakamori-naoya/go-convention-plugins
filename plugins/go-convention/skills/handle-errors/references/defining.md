# 具体エラーの定義

# どこから生まれるか

## 業務の拒否は、資料の拒む理由から

業務の拒否は、ドメインモデルの資料のコマンドの節にある拒む理由から生まれる。拒む理由一つに、具体エラー一つを定義する。同じ理由が複数のコマンドに現れるなら、具体エラーは一つにする。受けない状態から呼ばれたときの拒む理由も、同じ節に一文で書かれているので、同じように定義する。

分類は、ほとんどが「業務ルールに反する」になる。資料の拒否が対象の不在を表すなら「存在しない」、同じものの重複を表すなら「すでに存在する」、主体に許されていないことを表すなら「許可されていない」を選ぶ。

```go
// 図書館の貸出。資料の「本を借りる」「本を返す」「延滞にする」の拒む理由に一つずつ対応する。
var (
	ErrUserHasOverdue   = errors.Wrap(errors.ErrPrecondition, "延滞の貸出がある利用者が本を借りる")
	ErrLoanLimitReached = errors.Wrap(errors.ErrPrecondition, "貸出上限に達している利用者が本を借りる")
	ErrAlreadyReturned  = errors.Wrap(errors.ErrPrecondition, "返却済みの本を返す")
	ErrNotPastDue       = errors.Wrap(errors.ErrPrecondition, "返却期限を過ぎていない貸出を延滞にする")
)
```

資料に無い業務の拒否は、定義しない。要ると感じたら止まり、資料の持ち主へ「拒む理由の追加」として提案する。業務の規則を実装の側で足すと、資料と実装が食い違い、その食い違いは誰も管理しないからである。

## 値の構造の拒否は、値オブジェクトの不変条件から

空の識別子、形式の違う文字列、範囲外の数のように、値の構造として必ず拒む値は、資料に書かれていなくても、値オブジェクトの生成が拒んでよい。これは業務の規則ではなく、その値の不変条件だからである。分類は「入力が不正」にする。

```go
var ErrUserNoMalformed = errors.Wrap(errors.ErrInvalidInput, "利用者番号の形式が正しくない")
```

## 集約の外で守る不変条件

一つの集約の中では確かめられない不変条件（一冊の本は同時に一つの貸出にしか属さない、など）は、DB の制約が最後に守る。その制約の違反は、リポジトリの翻訳表で、資料の拒む理由の具体エラーへ写す（[運び方、翻訳、付け替え](propagation.md)）。事前に確かめたときと、同時に起きたときで、利用者から見た結果は同じなので、具体エラーも一つにする。どの制約で守るかは、物理設計の資料が決める。

# 名前と文言

具体エラーの名前は、`Err` の接頭辞と、何が拒まれたかで付ける（`ErrLoanLimitReached`）。

文言は、資料の拒む理由の語をそのまま使う。言い換えると、資料との対応を辿れなくなり、言い換えのたびに意味がずれる。値の構造の拒否の文言は、どの値の何が拒まれたかを、句点なしの一文で書く。

文言は、応答で利用者に見せてよい内容だけにする。個人を識別する値、秘密、SQL、外部のライブラリの文言を入れない。どの ID の操作かのような文脈は、文言ではなく記録の属性で運ぶ（write-logs が定める）。

コメントには、その値がどの業務の条件に反するかを業務の言葉で書く。「資料に無い」「言語の都合」のように、存在の理由を実装の事情に帰する断り書きは書かない。

# 拒まないが何も変えない操作は、エラーではない

資料が「拒む理由は無く、条件を満たさなければ何も変えない」と書く操作は、エラーではなく `(Result, bool)` で返す。何も起きなかったことは失敗ではない。これをエラーにすると、境界が毎回それを拒否として記録してしまう。

# 置き場

具体エラーは、それを返す package の `errors.go` に並べる。値オブジェクトのエラーは値オブジェクトの package に、集約のエラーは集約の package に、翻訳や付け替えで使うエラーはリポジトリの package に置く。interface の契約に固有のエラーは、その interface のファイルに置く。
