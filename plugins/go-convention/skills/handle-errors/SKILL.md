# handle-errors

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

「拒まれたこと、できなかったこと」を、起きた場所から最も外の境界まで、判定できる形で運ぶ。読み終えると、エラーを定義し、運び、外部のエラーを翻訳し、境界で応答と処理を決められる。

中心にあるのは一つの考えである。**すべてのエラーは、閉じた15の分類のどれか一つを、定義の場所で選ぶ。** 境界は分類だけを見て、表から応答と処理を決める。分類をキーにした表は閉じた集合なので、表が漏れなく分類を持つことを検査できる。エラーごとの sentinel をキーにした表は開いた集合で、載せ忘れた sentinel が黙って落ちる。

この規約が持つのは、15の分類、具体エラーの定義の形、運び方、翻訳、分類の付け替え、応答の表と処理の表である。ログレベルの意味、分類からレベルへの表、どこで記録するかは write-logs が持つ。

## 入力

対象の package と、その package が返す拒否の根拠になる資料を受け取る。業務の拒否の根拠は、業務知識の資料の「拒むときの理由」である。どのコマンドがどの理由で拒むか（受けない状態から呼ばれたときを含む）は、ドメインモデルの資料から、その対応として読む。ドメインモデルが業務知識への提案に回した拒む理由は、まだ根拠ではないので定義せず、止まる候補にする。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約は、対象 repository の AGENTS.md / CLAUDE.md と `references` で渡される。

## 判断基準

### 分類を一つ選ぶ

具体エラーは、[エラーの分類](references/categories.md)の15の分類から一つを選び、`errors.Define(分類, 文言)` で定義する。`errors.Define` は、分類に文言を付けて新しい具体エラーを作る関数であり、既存のエラーを包む関数ではない。既存のエラーを包むのは、翻訳と付け替えのときの `fmt.Errorf` だけである。分類の意味の境目（「業務ルールに反する」と「利用上限に達した」の違いなど）も、そこに書いてある。分類の package がまだ無いなら、そこにある形で作る。

### 業務の拒否は資料から、値の構造の拒否は値オブジェクトから

資料に無い拒否には、二種類ある。値の構造として必ず拒む値（空の識別子、形式の違う文字列）は、資料に書かれていなくても値オブジェクトの生成が拒んでよく、「入力が不正」に分類する。業務の規則による拒否は、資料にあるものだけを実装する。資料に無い業務の拒否が要ると感じたら、作らずに止まる。詳しくは [具体エラーの定義](references/defining.md) を読む。

### 包まずに運び、翻訳と付け替えのときだけ包む

具体エラーは分類と文言を自分で持つので、層を越えるときに包まずに返す。包むのは二つの場面だけである。外部のライブラリのエラーを翻訳表で分類へ写すときと、値の出どころに合わせて分類を付け替えるときである。一つのエラーの連鎖が持つ分類は、一つだけにする。詳しくは [運び方、翻訳、付け替え](references/propagation.md) を読む。

### 境界は表で決める

境界は、分類から応答の表で Connect の Code を、処理の表で「再試行で通りうるか」と「失敗が全体に及ぶか」を決める。三つ目の表（ログレベル）は write-logs が持つ。三つの表は別々の関心なので、一つの割り当てから別のものを導かない。詳しくは [境界の表](references/tables.md) を読む。

## 手順

1. **根拠を集める。** `references` があれば先に読む。対象の package が返す拒否を、業務知識の「拒むときの理由」と、ドメインモデルが示すコマンドとの対応と、値オブジェクトの生成の条件から集める。
2. **分類を選んで定義する。** 拒否ごとに分類を一つ選び、名前と文言を [具体エラーの定義](references/defining.md) の規則で決めて、package の `errors.go` に並べる。資料に無い業務の拒否は、定義せずに止まる候補として残す。
3. **運び方を揃える。** 層を越える `return` で包んでいる箇所を外す。複数の失敗を一つのエラーに結合している箇所を、[運び方、翻訳、付け替え](references/propagation.md) の形に直す。
4. **翻訳と付け替えを置く。** 外部のライブラリのエラーを、翻訳表で分類へ写す。保存値や設定値を値オブジェクトが拒んだ箇所で、分類を付け替える。
5. **境界の表を確かめる。** 応答の表と処理の表が15の分類を過不足なく持ち、網羅のテストがあることを確かめる。無ければ [境界の表](references/tables.md) の形で置く。
6. **機械検査を通す。** `go vet ./...`、`go tool golangci-lint run ./...`（標準の `errors` の import の禁止を含む）、表の網羅のテストが通る。
7. **報告する。** 出力の項目を返す。

## 停止条件

資料に無い業務の拒否が要ると判断したら、定義せずに止まり、資料の持ち主へ「拒む理由の追加」として提案する。受けない状態の拒む理由が資料に無いときも同じである。エラーを既定値に丸めたくなったとき、失敗したら別の経路で続けたくなったときは、書かずに止まり、何を丸めたいか、なぜ error で返せないかを示して、利用者の許可を得てから書く。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

名前や文言の言い回しの揺れでは止まらない。規則から最も筋の良いものを採り、報告に示して進む。

## 出力

定義した具体エラーと、それぞれの分類と根拠（資料の拒む理由の語、または値の不変条件）、置いた翻訳（外部のエラーと写した分類）と付け替えの箇所、応答の表と処理の表の変更、機械検査の結果、資料へ返した拒否の提案を報告する。

機械検査が通って言えるのは、標準の `errors` を分類の package の外で import していないこと、二つの表が15の分類を網羅していること、vet と linter の検査に違反が無いことだけである。分類の選び方が意味として正しいか、文言が資料の語と一致するかは、対象を読んで報告する。
