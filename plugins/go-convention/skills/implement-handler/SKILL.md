# implement-handler

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

外から来た要求を usecase の入力へ写し、usecase を一つ呼び、結果を応答へ写す、薄い入口を書く。読み終えると、入口で何を変換し、何を interceptor に任せ、どう組み立てて起動するかを決められる。

中心にあるのは二つの考えである。一つは、**値オブジェクトへの変換と、業務の時刻の取得は、入口で一度だけ行う**ことである。usecase は検証済みの値だけを受け取る。もう一つは、**入口は判断せず、記録せず、翻訳しない**ことである。判断は集約が、翻訳と記録は最も外の interceptor が一度だけ行う。

## 入力

proto と生成したコード、対象の RPC（または受信境界、巡回）、呼ぶ usecase の入力と出力を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

前提は Go 1.27、`connectrpc.com/connect` v1、`google.golang.org/protobuf` である。

先に赤いテストがある場面も通常である。テストが前提にする組み立ての関数、Code、公開の文言に合わせ、テストを変えずに緑にする実装を書く。

## 判断基準

### 入口

要求のプリミティブを値オブジェクトへ変換し、欠けた値を丸めない。業務の時刻は入口の Clock から一度だけ取る。主体は認可の interceptor が解決したものを使う。一つの RPC は一つの usecase を呼び、エラーはそのまま返す。ワーカーが一定の間隔で対象を探して処理する巡回は、query で候補を選び、一件ずつ command を呼び、一件の失敗をほかの件に広げない。詳しくは [入口](references/entrance.md) を読む。

### interceptor

外から、記録と翻訳、認証、認可、頻度の制限の順に並べる。認可は手続きごとの方針の表で主体を解決し、表に無い手続きを拒む。トークンの検証は外部の境界のポートに任せる。詳しくは [interceptor](references/interceptors.md) を読む。

### 組み立てと起動

`main` はシグナルと logger と終了コードだけを持ち、`run` が環境で変わるものを作り、組み立ての関数が内側から外側へ全部を組み立てる。本番とテストが同じ組み立ての関数を呼ぶ。設定は名前付きの型で読み込み、欠けていれば起動しない。詳しくは [組み立てと起動](references/wiring.md) を読む。

## 手順

1. **入口の形を決める。** `references` があれば先に読む。対象が RPC、受信境界、巡回のどれかと、呼ぶ usecase を確かめる。
2. **変換を書く。** 要求から値オブジェクトへの変換と、usecase の出力から応答への変換を書く。業務の時刻と主体の出どころを決める。
3. **入口を書く。**
4. **interceptor と方針の表を確かめる。** 新しい手続きを、認可の方針の表に足す。頻度の制限を置くかを、資料で確かめる。
5. **組み立てに足す。** 組み立ての関数に、新しい usecase と入口を配線する。
6. **機械検査を通す。**
   ```bash
   go build ./... && go vet ./...
   go tool golangci-lint run ./...
   ```
7. **報告する。** 出力の項目を返す。

## 停止条件

usecase に無い入力や出力が要るときは、implement-usecase へ返す。入口で業務の判断や本人の確認が要ると感じたら、集約のコマンドの事前条件として implement-domain-model と資料へ返す。どの RPC に頻度の制限や認可の方針を置くかが資料に無いときは、資料の持ち主へ問う。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

## 出力

書いた入口と、それが呼ぶ usecase、値オブジェクトへの変換と時刻と主体の出どころ、方針の表への追加、組み立ての変更、返した論点、機械検査の結果を報告する。

機械検査が通って言えるのは、ビルド、vet、linter に違反が無いことだけである。入口が判断していないこと、Code と文言が正しいことは、test-handler の API のテストと、対象を読んで確かめる。
