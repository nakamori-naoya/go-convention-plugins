# 突き合わせる範囲

データモデルの資料は、BDD ごとに、その When で読み書きするテーブルと、変わらないことを確かめるテーブルだけを、Before と After の具体的な行で示す。資料の Before と After は議論のための具体例であり、全テーブルは並べない。

リポジトリのテストは、資料と食い違わず、資料の書き方には縛られすぎない形で、次の二つを確かめる。

# 資料が挙げたテーブルは、全行と全列

資料が After に挙げたテーブルは、全行と全列を、資料の After と突き合わせる。行が一件多くても少なくても、失敗にする。これで、テストと資料の After が食い違わないことが保証される。拒まれるケース（何も記録されない）では、After は Before と同じ行である。

期待の値は、資料の表の値を写す。資料の識別子（`L-001`、`E-001`）は、テストの側で固定の UUID に名前を付けた `const` に対応させ、採番器の mock がその値を返すようにする。時点は UTC で書く。

# 資料が挙げていないテーブルは、行数が変わらない

資料が挙げていないテーブルに、意図しない書き込みが無いことも確かめる。資料には書かれていない、テストの側の検証である。

アプリケーションのテーブルのうち、資料がその BDD に挙げていないものの行数が、When の前後で変わらないことを、一つの支援関数で確かめる。対象のテーブルは、資料から列挙せず、DB のカタログから取る。資料にテーブルを足さなくても、新しいテーブルへの意図しない書き込みを見つけられるようにするためである。

```go
before := dbassert.CountRowsExcept(t, suite.Reader, "loans", "loan_base_events", "loan_lent_events")
// When
dbassert.RequireRowCountsUnchanged(t, suite.Reader, before)
```

# Before は持ち主の書き込み経路で作る

Before の行は、持ち主のコマンドと書き込み経路を順に通して作る（apply-go-test-convention のテストデータの規則）。「5冊借りている利用者」なら、本を借りるを五回、実物の集約と実物のリポジトリで通す。延滞の貸出なら、本を借りる → `ApplyLent` → 延滞にする → `ApplyOverdue` を通す。Before を作るときの時刻と識別子は、Clock と採番器の mock が資料の値を返すようにする。

行を直接入れてよいのは、保存値の破損を検出するテストだけである。その行は、目的を名前にした最小の行にする。

資料の Before に無いテーブルに前提の行が要ると、テストを書く途中で気付いたら、テストの側で行を足して辻褄を合わせない。資料の BDD へ提案として返す。

# 行を読むテスト専用の SQL

テストが行を読むための SQL（全行を主キー順に読む、行数を数える）は、本番の SQL と別の query のファイル（例：`db/query/<context>_<aggregate>_test_support.sql`）に書き、本番と別の生成の package に生成する。テストはその package だけを import し、本番の生成の package を import しない。本番のコードは、テスト専用の生成の package を import しない。この向きは lint で拒む。テストの本文に、生の SQL や pgx の `Query` を書かない。
