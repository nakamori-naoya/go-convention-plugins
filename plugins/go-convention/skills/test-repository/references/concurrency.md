# 同時に起きたとき

資料の「同時に起きたとき」の BDD は、二つの操作の順序を、バリアで固定して起こす。タイミングに頼るテスト（ロックの待ちを時間で観測する、goroutine がたまたま先に走ることを期待する）は書かない。安定して再現できないからである。待つときは、testing-strategy の待機の原則に従い、観測できる条件で、期限を付けて待つ。

# 形

二つの操作を、それぞれ別のトランザクションで始め、両方が材料を読み終えたところをバリアで揃えてから、一方を先に確定させ、他方を後で確定させる。先に確定した方が成立し、後の方が物理設計の決めた結果（一意制約の違反、直列化の失敗）になることを確かめる。

```go
// 二つの借りる操作が、どちらも「まだ貸出中でない」と読み終えたところで揃える。
bothRead := make(chan struct{})
var readers sync.WaitGroup
readers.Add(2)
// 一つ目：読み終えたら揃うのを待ち、先に確定する。
// 二つ目：読み終えたら揃うのを待ち、一つ目の確定を待ってから確定する。
```

goroutine の中では `require` を呼ばず、エラーを変数に受けて、`Wait` の後に確かめる（apply-go-test-convention の Then の規則）。

物理設計が直列化の失敗のやり直しを指定しているなら、後の方はやり直しの後で業務の結果（「貸出上限に達している利用者が本を借りる」）になる。テストは、その業務の結果と、資料の After を確かめる。

# 版の衝突は、順に起こせる

同じ版を読んだ二つの操作の衝突（延滞にするのと返却が重なる）は、並走させなくても再現できる。古い版の集約を `Restore*` で持ったまま、先に新しい版を記録し、その後に古い版のコマンドの結果を `Apply` する。後の方が一意制約の違反になり、「同時更新で競合した」が返ることを確かめる。並走させない形で再現できるなら、そちらを選ぶ。

# 同時の回収は、順に起こせる

同じ要求を二つの送り手が同時に回収する場面（BDD-009）は、物理設計が一意制約で守ると決めているので、版の衝突と同じく並走させずに再現できる。同じ候補を `ListClaimable` で二度得ておき、一つ目のトランザクションで `Claim` を確定させた後、二つ目のトランザクションで同じ候補の `Claim` を呼ぶ。二つ目が「同時更新で競合した」を返すことと、回収の行が一行だけであること（After）を確かめる。物理設計が `FOR UPDATE SKIP LOCKED` を足したなら、確かめることは、二つ目の `ListClaimable` がその要求を返さないことに変わる。
