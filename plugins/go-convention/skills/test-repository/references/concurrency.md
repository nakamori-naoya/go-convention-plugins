# 同時に起きたとき

資料の「同時に起きたとき」の BDD も、一つのテストの中で、二つのトランザクションを決めた順に進めて起こす。goroutine を並べて走らせ、どちらが先に進むかやロックの待ちに頼るテストは書かない。実行順が毎回変わるので、同じ結果を安定して再現できないからである。

# 二つのトランザクションを交互に進める

二つの操作を、それぞれ別のトランザクションで始める。どちらも材料を読み終えるところまで進めてから、一つ目を確定させ、その後に二つ目の書き込みと確定を行う。どの時点で何をしたかがコードの順序で決まるので、先に確定した方が成立し、後の方が物理設計の決めた結果（一意制約の違反、直列化の失敗）になることを、毎回同じように確かめられる。

一つ目を確定させる前に二つ目で同じ行へ書き込むと、二つ目はロックを待ち、同じ goroutine の中では先へ進めなくなる。書き込みは、一つ目の確定の後に置く。

同じ利用者が同時に二冊を借りる場面なら、二つのトランザクションでそれぞれ貸出状況を読み、一つ目の貸出を記録して確定させ、二つ目の貸出を記録して確定させる。物理設計が `SERIALIZABLE` を指定しているので、二つ目は直列化の失敗になる。物理設計がそのやり直しを指定しているなら、やり直した後の業務の結果（「貸出上限に達している利用者が本を借りる」）と、資料の After を確かめる。

同じ本を二人が同時に借りる場面なら、二つのトランザクションでそれぞれ貸出状況を読み、一つ目の貸出を記録して確定させた後に、二つ目の貸出を記録する。部分一意の制約の違反が、「貸出中の本を借りる」へ翻訳されることを確かめる。

# 版の衝突は、古い版の結果を後から適用して起こす

同じ版を読んだ二つの操作の衝突（延滞にするのと返却が重なる）は、トランザクションを重ねなくても再現できる。古い版の集約を `Restore*` で持ったまま、先に新しい版を記録し、その後に古い版のコマンドの結果を `Apply` する。後の方が一意制約の違反か、読んだ版を条件にした更新の0件になり、「同時更新で競合した」が返ることを確かめる。

# 同時の回収も、先の確定の後に同じ候補を回収して起こす

同じ要求を二つの送り手が同時に回収する場面（BDD-009）は、物理設計が一意制約で守ると決めているので、版の衝突と同じく順に再現できる。同じ候補を `ListClaimable` で二度得ておき、一つ目のトランザクションで `Claim` を確定させた後、二つ目のトランザクションで同じ候補の `Claim` を呼ぶ。二つ目が「同時更新で競合した」を返すことと、回収の行が一行だけであること（After）を確かめる。物理設計が `FOR UPDATE SKIP LOCKED` を足したなら、確かめることは、二つ目の `ListClaimable` がその要求を返さないことに変わる。
