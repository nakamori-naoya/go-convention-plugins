# develop-query-service

中心にあるのは二つの考えである。**返すものはクエリデータモデルが、速く返すための形は物理設計が決め、コードはそれを写す。** どのテーブルをどう組み合わせ、何を対象に選び、どの順で返すかはクエリデータモデルの BDD が、index、読み取り元、読み取りの SQL の一覧は物理設計が決め、食い違ったら資料の持ち主へ返す。**クエリサービスは読むだけで、判断も書き込みもしない。** 業務の判断はコマンドが、保存はリポジトリが持つ。返すものが、コマンドを呼べる集約ならリポジトリの Find の関心で、表示や選択のための読み取りモデルならこの skill の関心である。

進め方と赤は development-convention の `develop-inside-out` に、読み取り専用の接続と翻訳の契約は apply-crosscutting-contracts に、記録は write-logs、テストの共通の形は apply-go-test-convention に従う。延滞の一覧を題材にした形は [貸出の Query の例](references/example.md) にある。

## 読み取りの形：読み取り専用の接続だけから読む

Query の実装は、usecase の側が所有する読み取りのポートを満たし、読み取り専用の接続だけから読み、集約を復元せず、書き込まず、トランザクションを張らない。射影、結合、件数、集計は SQL で行い、SQL で書けない業務の計算は値オブジェクトか純関数を借り、根拠が資料に無い計算は書かない。SQL は sqlc の query のファイルにだけ書き、読み取りは物理設計の読み取りの一覧（Read-001 のような）に載っているものに限る。載っていない読み取りが要るなら、足さずに物理設計の資料へ返す。

業務上の順位と同順位の扱いはクエリデータモデルが決め、並びの SQL はそれをそのまま写す。同順位の扱いが資料に無く、それで返す順が変わるなら、並びを発明せずに資料へ返す。

## 壊れた一件を除き、ページの目印は走査した候補で決める

互いに独立した複数件を返すときは、保存値を値オブジェクトへ戻せない一件だけを除き、除いた場所で ERROR で記録して残りを返す。そのために logger を注入される。一覧全体を失敗させず、壊れた値を正常な値へ丸めない。クエリそのものの失敗は全体を失敗させる。ページの目印は、返せた件数ではなく走査した候補の境界で決める。壊れた一件を除いた分だけ目印を手前にすると、次のページで同じ候補を読み直すからである。作業待ちの行を読むのは永続化の手順の口で、クエリサービスは読まない。

## テスト：実物の PostgreSQL で、資料の取得結果と突き合わせる

取得のテストが主に担うのは、`Then:` が取得結果を観測するクエリデータモデルの BDD である。Before は持ち主の書き込み経路で作り（例外は apply-go-test-convention が持つ）、読み取りのポートを本番と同じ読み取り専用の接続で組んで呼び、取得結果を `assert.Equal` で突き合わせる。資料に無いケースとして、絞り込み、並び、ページ、空、壊れた一件を除くことを足す。

取得のテストは、返る行と同じだけ、返してはいけない行が返らないことを確かめる。返る行しか置かないケースは、絞り込みの条件を一つ外した実装でも緑になるからである。実装の読み取りの条件（誰の、どの対象の、どの期間の、どの種類の、どの閾値の）を挙げ、条件ごとに、その条件だけを外れて残りをすべて満たす行を置く。いくつかの値の組で決まる区分（年と月と区切り、など）には、値ごとに一つだけ違う行（隣の区切り、前年の同じ区切り）を、閾値には返らない側で最も近い値（「より前」ならちょうどの値、「以上」なら一つ手前の値）を置き、どの条件にも関係しない主体の行（対象外の利用者どうしや、対象外の利用者が関わる相手の行）も置く。これらの返してはいけない行は、専用の一ケースではなく、どのケースにも共通の Before として apply-go-test-convention の作り方で作る。専用の一ケースにだけ置くと、ほかのケースが確かめる条件の取り違えを見つけられないからである。返る側の境界の値は共通の Before に置かず、それを確かめるケースの Given に置く。値は業務で起こり得るものにし、紛れ込めば取得結果が変わるものを選ぶ（合計なら0でない値、最大の一件を選ぶなら、どのケースの値よりも大きい値、一回に返す件数に上限があるなら、その上限の内側に並ぶ値）。共通の行の値と識別子は、各ケースの Given と重ならないようにする。重なると、期待がケースの Given だけで決まらなくなる。

並びのケースは、書き込む順と返す順が一致しないように Before を作り、同順位の行を置いて資料どおりの順を確かめる。書き込む順と返す順がそろっていると、並びの SQL が抜けても書き込みの順で偶然そろって緑になるからである。ページのケースは、ページの境界の前後の行と、境界の位置に壊れた一件がある場合の次の目印を確かめる。並びが複数の列で決まるなら、目印もその列の組で決め、同順位の行が境界をまたいでも、次のページで重複も抜けも起きないことを確かめる。

置いた行が効いているかは、実装の条件（絞り込み、並び）を一つずつ外し、テストが赤になるのを見てから実装を戻して確かめる。赤にならない条件は、行が足りないか、その条件が取得結果を変えない（読む範囲を狭めるためだけの絞り込みや、同じ事実を別の列で重ねて絞る条件）かのどちらかである。前者なら行を足し、後者なら理由を報告に書く。

確かめないのは、業務の判断（ドメイン）、書き込みと制約とトランザクション（永続化）、入力からどのポートを呼ぶかの選択（usecase）、Code と文言（入口）、読み取りの速さ（物理設計の計測）である。同じ実 DB を共有するので直列で走らせる。

## 止まるとき

クエリデータモデルの BDD に Before と取得結果の表が無いとき、物理設計の読み取りの一覧に無い読み取りが要るとき、同順位の扱いが資料に無く返す順が変わるとき、根拠が資料に無い計算が要るとき、読み取りのポートに無いメソッド（件数、存在の確認）が要るときは、その欠落で結論が変わる部分だけを書かずに資料か持ち主へ返し、独立して決まる部分（同順位の扱いが欠けていても、絞り込み）は進める。query や変換の関数の名前の揺れでは止まらない。報告には、メソッドごとに読むテーブル、読み取りの一覧との対応、除いた壊れた一件の扱い、条件を外しても赤にならなかった条件とその理由、テストが主に担う BDD の ID を書く。
