# test-handler

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

RPC の公開の結果を、本番と同じ組み立てを通して確かめる。読み終えると、API のテストをどう起動し、何を確かめるかを決められる。

中心にあるのは一つの考えである。**API のテストは、本番の組み立てを通す。** interceptor の列、変換、usecase、リポジトリを本番と同じ順に並べ、差し替えるのは制御できない外部の境界と時計と採番だけにする。

テストの形、実 DB の基盤、テストデータ、差し替えてよい境界、BDD の写し方は、apply-go-test-convention に従う。

## 入力

対象の RPC、組み立ての関数、handle-errors の応答の表、業務知識の資料の絶対 path を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

テストを書く場面は二つあり、どちらも通常である。テストが先の場面では、proto と資料から名前を決めて書き、コンパイルエラーで赤になる状態を正とする。

## 判断基準

### 起動と差し替え

本番と同じ組み立ての関数で起動し、生成したクライアントで叩く。差し替えは、外部のトークン検証のポート、時計、採番器だけで、主体は Authorization のヘッダで決める。詳しくは [起動と差し替え](references/setup.md) を読む。

### 何を確かめるか

成功と反映、分類ごとの Code と公開の文言、認証と認可、入口での変換を確かめる。API のテストが主に担う BDD（他人の利用者カード）は、資料の ID で写す。詳しくは [何をテストするか](references/what-to-test.md) を読む。

## 手順

1. **起動を確かめる。** `references` があれば先に読む。組み立ての関数と、差し替える三つの境界と、実 DB の基盤を確かめる。
2. **ケースを選ぶ。** 成功、その RPC が返しうる分類ごとの Code と文言、主体の無い要求、方針に合わない主体、欠けた入力を並べる。
3. **表を書く。** 前提（持ち主の書き込み経路）、主体、要求、期待の Code と文言、期待の応答、反映を見るテーブルを並べる。
4. **ループ本体を書く。** 前提を作る → 叩く → Code と文言か応答を確かめる → 反映を確かめる、を一回書く。
5. **機械検査を通す。**
   ```bash
   go vet ./...
   go test -count=1 ./<handler package>/...
   ```
   テストの形の検査と、repository 全体の BDD の網羅の検査は、apply-go-test-convention の tool で行う。
6. **報告する。** 出力の項目を返す。

## 停止条件

組み立ての関数が無く、本番と同じ組み立てを呼べないときは、implement-handler へ返す。interceptor を差し替えないとテストが書けないときは、外部の境界のポートの切り方の不足として implement-handler へ返す。応答の表に無い分類を確かめたくなったときは、handle-errors へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

## 出力

対象の RPC とテスト関数、確かめた公開の結果の一覧、主に担う BDD の ID、差し替えた境界、機械検査の結果、返した論点を報告する。

機械検査が通って言えるのは、本番の組み立ての上で全ケースが通ったことと、テストの形と BDD の網羅の構造だけである。公開の結果をひととおり確かめたかは、対象を読んで報告する。
