# 何をテストするか

API のテストは、RPC を公開の API として叩き、その RPC が持つ公開の結果を、ひととおり確かめる。

# 主に担う BDD

API のテストが主に担うのは、`Then:` が、認証、認可、応答の Code、入口での変換を観測する BDD である。図書館では、「他人の利用者カードでは本を借りられない」がこれに当たる。これらは資料の ID で写す（apply-go-test-convention）。ほかのレベルが主に担う BDD の場面を公開の API から見るケースは、生成した id を使う。

# 確かめること

**成功。** 応答の中身と、成功が DB に反映されたこと（一つの代表的なテーブル）。

**Code と公開の文言。** その RPC が返しうる分類ごとに、応答の Code と公開の文言が、handle-errors の応答の表と、具体エラーの文言どおりであること。同じ Code でも、文言を決める具体エラーが違う経路は、別のケースで確かめる。回復不能と分類不能は、固定の文言だけが返り、内部の文言が出ないこと。

**認証と認可。** 主体の無い要求が「認証されていない」になること。方針の表が求める主体でない要求（登録していない利用者）が拒まれること。

**入口での変換。** 要求の欠けた値や形の違う値が、「入力が不正」になること。

# 確かめないこと

業務の判断の境界（ドメインのテスト）、行の全列と SQL（永続化層のテスト）、トランザクションの境界（usecase のテスト）、ログが出たか、は確かめない。同じ公開の結果の経路に、入力の値だけを変えたケースを並べない。
