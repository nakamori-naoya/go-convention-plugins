# develop-repository

中心にあるのは二つの考えである。**資料が決めたテーブルの型と制約をそのまま写す。** テーブル、列、制約はコマンドデータモデルが、読み取りが返すもの（組み合わせ、表示対象、並び順）はクエリデータモデルが、分離レベル、index、読み取りの SQL の一覧は物理設計が決め、食い違ったら資料の持ち主へ返す。物理設計が操作ごとに決めた業務の結果（更新が0件のとき、外部キー、一意制約、CHECK の違反、やり直しの扱い）は、この skill の既定より優先する。下に書いた結果は、物理設計が決めていないときの既定である。**永続化層は判断しない。** Find は読んで値にするだけで、判断はコマンドが、トランザクションは usecase が持つ。

進め方と赤は development-convention の `develop-inside-out` に、トランザクション、翻訳、時計、ID ジェネレーターの契約は apply-crosscutting-contracts に、付け替えは handle-errors、テストの共通の形は apply-go-test-convention に従う。例は [例：図書館の貸出の永続化](references/example.md) にある。

## テーブルの型を写す

集約は三つのテーブルに出来事を積む。**リソースのテーブル**は集約が生まれたときに決まる事実を持ち、生成の Apply が一行を追加する。リソースは現在の状態と版を列（`status`、`current_version`）に持つので、状態を変える Apply は、同じトランザクションで読んだ版を条件にその列を更新し、0件なら、物理設計が決めた業務の結果を、決めていなければ「同時更新で競合した」を返す。**基底イベントのテーブル**（`<対象>_base_events`）は、識別子、種類、版、出来事の時点（`occurred_at` の一列だけ）を持ち、Apply はどれも一行を追加する。**詳細イベントのテーブル**（`<対象>_<過去分詞>_events`）は出来事に固有の業務が与えた値を持ち、主キーは基底イベントの識別子で、固有の値が無くても一行を追加する。派生のテーブルがあれば同じトランザクションで更新する。

版はイベントの版をそのまま書き、同じ版の一意制約の違反は「同時更新で競合した」へ翻訳する。`occurred_at` は、イベントがコマンドの判断に使った時点を持てばその値、持たなければ Apply が時計から一度だけ取った値を、同じ操作の全部の行に写す。判断に使わない時刻をドメインから受け取らず、ここに閉じ込める（基準は development-convention の `apply-layer-convention`）。後続の要求を伴うイベントなら、同じトランザクションで Outbox の要求の行も追加する。値の範囲の CHECK は、ドメインモデルが値の正しさを持つ業務のテーブルには置かない。

## リポジトリ：Find は判断せず、Apply は error だけを返す

どのメソッドも、ctx のトランザクションから sqlc の `Queries` を組む。`Find<返す型>` は、コマンドを直ちに呼べる完全な集約を一つ返す。保存された状態なら行の状態から型を選んで `Restore*` で組み、行が無ければ「存在しない」（初期状態の型を和型に入れた集約では、材料を集めた初期状態の型）、知らない状態の値は保存値の破損とする。初期状態の型なら、判断に要る外の事実を読んで持たせるだけで、上限を見て拒んだり読み方を変えたりしない。資料が値の選び方（閾値、経路）を定めていても、リポジトリで判断せず、コマンドが決めてイベントに載せる形を返す。`Apply<イベント名>` は error だけを返す。

行からドメインへは `New*` を通し、拒まれたら「回復不能」へ付け替える。ドメインから行へは、リポジトリの直下の `marshaller` package の純粋な関数が、イベントと、一回の保存で共有する時刻と識別子から sqlc の引数を作る。名前は `<イベント>To<query>Params` にし、`Apply<イベント名>` は時刻と識別子を一度だけ取ってその関数の結果を query へ渡す。変換が時計も ID ジェネレーターも読まないので、同じ保存の全部の行に同じ値が写り、Apply にはどの行をどの順で書くかだけが残るからである。有限な値の列は値を所有する package の定義を使う。制約（一意、外部キー、CHECK）の違反から、物理設計が決めた業務の結果の具体エラーへの対応は、リポジトリが一つの `rdb.Constraints` で持つ。

SQL は sqlc の query のファイルにだけ書き、読み取りは物理設計の読み取りの一覧（Read-001 のような）に載っているものに限る。載っていない読み取りが要るなら、足さずに物理設計の資料へ返す。ロックを取る読み取りは物理設計が指定したときだけ書く。

## 手順の口：一度に確定させる一つの記録に一つのメソッド

手順が所有する口（Outbox の回収と完了の記録など）も ctx のトランザクションを必須にし、自分では張らない。口ごとに変えると、どこで確定したかを手順から読めなくなるからである。口は読み取りのポートを呼ばず、要る読み取りは自分の SQL で行う。口は判断せず、処理の段階で行を選んで記録を書くだけである。記録の時刻と識別子は口が時計と ID ジェネレーターから取る。

回収は一件ごとに別のトランザクションで確定させる。PostgreSQL では一意制約に違反したトランザクションはその場で中断するので、複数の回収を一つに入れると一件の衝突で残りもできなくなる。同じ回収の衝突は「同時更新で競合した」として返し、手順が一件に閉じた失敗として次へ進む。一つの要求の成功を一つにする守り方（一意制約、行のロック、確かめる順）は物理設計が決め、口はその順で SQL を呼ぶ。

## Query の実装：読み取り専用の接続だけから読み、壊れた一件を除く

Query の実装は、usecase の側が所有する読み取りのポートを満たし、読み取り専用の接続だけから読み、集約を復元せず、書き込まない。どのテーブルをどう組み合わせ、どの順で返すかはクエリデータモデルの BDD から写し、速く返すための形（index、読み取り元）は物理設計から写す。射影、結合、件数、集計は SQL で行い、SQL で書けない業務の計算は値オブジェクトか純関数を借り、根拠が資料に無い計算は書かない。

互いに独立した複数件を返すときは、保存値を値オブジェクトへ戻せない一件だけを除き、除いた場所で ERROR で記録して残りを返す。そのために logger を注入される。一覧全体を失敗させず、壊れた値を正常な値へ丸めない。クエリそのものの失敗は全体を失敗させる。ページの目印は、返せた件数ではなく走査した候補の境界で決める。作業待ちの行を読むのは手順の口で、黙って除かない。

## テスト：実物の PostgreSQL で、資料の After と突き合わせる

永続化層のテストが主に担うのは、`Then:` が記録される行、DB の制約が守る拒否、同時に起きたときの結果を観測するコマンドデータモデルの BDD と、取得結果を観測するクエリデータモデルの BDD である。物理設計が決めたやり直しの後の結果と、やり直しを使い切ったときの結果も、ここが観測する。集約が拒むものは、コマンドデータモデルに「記録されない」BDD として載っていてもドメインのテストが主に担う。

When は、Find で得た実物の集約のコマンドと実物の Apply で起こし、イベントを直接組み立てない。Before は持ち主の書き込み経路で作り（例外は apply-go-test-convention が持つ）、時刻と識別子は mock に資料の値を返させる。資料の識別子（`L-001`）は名前を付けた固定の UUID の文字列の `const` に対応させ、テスト関数の表の前で値オブジェクトと行の型へ一度ずつ変換する。期待する After は、コマンドデータモデルの After に、物理設計が同じ操作で変えると決めた表と列の行（どの操作で何行が、どの初めの値で変わるか）を重ねたものにする。その表は全行と全列を突き合わせ、どちらにも無いテーブルは DB のカタログから取って行数が変わらないことを確かめる。資料にテーブルを足さなくても、意図しない書き込みを見つけるためである。突き合わせには、テーブルごとに全行を主キー順に返す `List<テーブル>ForTest` を `*_test_support.sql` に書いて本番と別の生成の package へ sqlc で生成し、期待をその生成された行の型で書いて `assert.Equal` で比べる。SQL の文字列、map、列ごとの比較で書かない。列の型が変わればコンパイルが、期待に書いていない列に値が入れば突き合わせが失敗し、列の変化を黙って見落とさないからである。Before に無いテーブルに前提の行が要ると気付いたら、テストで辻褄を合わせずに資料へ提案する。

同時に起きたときの BDD は、物理設計が書いた経路をそのまま通して起こし、別の手順で代えない。代えると、資料が求める経路を通っていないのに確かめたことになるからである。割り込みで直列化に失敗する経路は、二つ目の要求を本番と同じトランザクションの管理と物理設計の `tx.Options` で張り、その最初の試行の中で、材料を読んだ後に一つ目を別のトランザクションで確定させる。やり直しの試行が読み直した材料で決めた結果を観測する。やり直しを使い切る経路は、毎回の試行の中で同じ割り込みを確定させる。行のロックで待つ経路は、一つ目がロックを持つ間に二つ目を goroutine で始め、二つ目がロックを待っていることを DB のカタログ（`pg_stat_activity` の待ちの種類）で確かめてから一つ目を確定させ、待っていた二つ目がそのまま続いた結果を観測する。期限で取り消して呼び直した結果では代えない。版の衝突は、古い版の集約を `Restore*` で持ったまま先に新しい版を記録し、その後に古い版の結果を Apply して起こす。

資料に無いケースとして、Find が状態ごとに正しい型を返すこと、初期状態の型の Find が外の事実を正しく読むこと、行が無い、保存値が壊れている、ctx にトランザクションが無い、を足す。Query の実装は、クエリデータモデルの Before を作って読み取りのポートを呼び、取得結果を `assert.Equal` で突き合わせ、絞り込み、並び、ページ、空、壊れた一件を除くことを確かめる。

## 止まるとき

資料に無いテーブル、列、制約、読み取りが要るとき、並行実行の保証がコマンドデータモデルにあるのに物理設計に守り方の指定が無いとき、コマンドデータモデルの BDD に Before と After の表が、クエリデータモデルの BDD に Before と取得結果の表が無いとき、前提を持ち主の書き込み経路で作れず apply-go-test-convention の例外にも当たらないとき、interface に無いメソッド（一覧、件数、存在の確認）が要るときは、書かずに資料か持ち主へ返す。物理設計がコマンドデータモデルに無い表か列を足したのに、どの操作で何行がどの初めの値で変わるかを書いていないときも、期待を推測せずに物理設計へ返す。query や変換の関数の名前の揺れでは止まらない。報告には、メソッドごとに読み書きするテーブル、時点の出どころ、翻訳の対応、読み取りの一覧との対応、テストが主に担う BDD の ID を書く。`rdb.Constraints` の一行ずつと `tx.Options` のやり直しの対象の一つずつには、それを実行で通したテストか、通らない理由（正しい実装では起きない、別の経路が先に効く）を書く。物理設計が二つの経路で同じ結果になると書いたときは、テストがどちらを通ったかを書き、通っていない方は理由に回す。
