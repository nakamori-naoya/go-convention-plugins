# develop-repository

中心にあるのは二つの考えである。**資料が決めたテーブルの型と制約をそのまま写す。** テーブル、列、制約はコマンドデータモデルが、読み取りが返すもの（組み合わせ、表示対象、並び順）はクエリデータモデルが、分離レベル、index、読み取りの SQL の一覧は物理設計が決め、食い違ったら資料の持ち主へ返す。**永続化層は判断しない。** Find は読んで値にするだけで、判断はコマンドが、トランザクションは usecase が持つ。

進め方と赤は development-convention の `develop-inside-out` に、トランザクション、翻訳、時計、採番の契約は apply-crosscutting-contracts に、付け替えは handle-errors、テストの共通の形は apply-go-test-convention に従う。例は [例：図書館の貸出の永続化](references/example.md) にある。

## テーブルの型を写す

集約は三つのテーブルに出来事を積む。**リソースのテーブル**は集約が生まれたときに決まる事実を持ち、生成の Apply が一行を追加する。リソースは現在の状態と版を列（`status`、`current_version`）に持つので、状態を変える Apply は、同じトランザクションで読んだ版を条件にその列を更新し、0件なら「同時更新で競合した」を返す。**基底イベントのテーブル**（`<対象>_base_events`）は、識別子、種類、版、出来事の時点（`occurred_at` の一列だけ）を持ち、Apply はどれも一行を追加する。**詳細イベントのテーブル**（`<対象>_<過去分詞>_events`）は出来事に固有の業務が与えた値を持ち、主キーは基底イベントの識別子で、固有の値が無くても一行を追加する。派生のテーブルがあれば同じトランザクションで更新する。

版はイベントの版をそのまま書き、同じ版の一意制約の違反は「同時更新で競合した」へ翻訳する。`occurred_at` は、イベントが業務の時刻を持てばその値、持たなければ時計から一度だけ取った値を、同じ操作の全部の行に写す。後続の要求を伴うイベントなら、同じトランザクションで Outbox の要求の行も追加する。値の範囲の CHECK は、ドメインモデルが値の正しさを持つ業務のテーブルには置かない。

## リポジトリ：Find は判断せず、Apply は error だけを返す

どのメソッドも、ctx のトランザクションから sqlc の `Queries` を組む。`Find<返す型>` は、コマンドを直ちに呼べる完全な集約を一つ返す。保存された状態なら行の状態から型を選んで `Restore*` で組み、行が無ければ「存在しない」、知らない状態の値は保存値の破損とする。初期状態の型なら、判断に要る外の事実を読んで持たせるだけで、上限を見て拒んだり読み方を変えたりしない。資料が値の選び方（閾値、経路）を定めていても、リポジトリで判断せず、コマンドが決めてイベントに載せる形を返す。`Apply<イベント名>` は error だけを返す。

行からドメインへは `New*` を通し、拒まれたら「回復不能」へ付け替える。ドメインから行へは、イベントの取り出しの関数で値を取って写し、有限な値の列は値を所有する package の定義を使う。一意制約から具体エラーへの対応は、リポジトリが一つの `rdb.Constraints` で持つ。

SQL は sqlc の query のファイルにだけ書き、読み取りは物理設計の読み取りの一覧（Read-001 のような）に載っているものに限る。載っていない読み取りが要るなら、足さずに物理設計の資料へ返す。ロックを取る読み取りは物理設計が指定したときだけ書く。

## 手順の口：一度に確定させる一つの記録に一つのメソッド

手順が所有する口（Outbox の回収と完了の記録など）も ctx のトランザクションを必須にし、自分では張らない。口ごとに変えると、どこで確定したかを手順から読めなくなるからである。口は読み取りのポートを呼ばず、要る読み取りは自分の SQL で行う。口は判断せず、処理の段階で行を選んで記録を書くだけである。記録の時刻と識別子は口が時計と採番器から取る。

回収は一件ごとに別のトランザクションで確定させる。PostgreSQL では一意制約に違反したトランザクションはその場で中断するので、複数の回収を一つに入れると一件の衝突で残りもできなくなる。同じ回収の衝突は「同時更新で競合した」として返し、手順が一件に閉じた失敗として次へ進む。一つの要求の成功を一つにする守り方（一意制約、行のロック、確かめる順）は物理設計が決め、口はその順で SQL を呼ぶ。

## Query の実装：読み取り専用の接続だけから読み、壊れた一件を除く

Query の実装は、usecase の側が所有する読み取りのポートを満たし、読み取り専用の接続だけから読み、集約を復元せず、書き込まない。どのテーブルをどう組み合わせ、どの順で返すかはクエリデータモデルの BDD から写し、速く返すための形（index、読み取り元）は物理設計から写す。射影、結合、件数、集計は SQL で行い、SQL で書けない業務の計算は値オブジェクトか純関数を借り、根拠が資料に無い計算は書かない。

互いに独立した複数件を返すときは、保存値を値オブジェクトへ戻せない一件だけを除き、除いた場所で ERROR で記録して残りを返す。そのために logger を注入される。一覧全体を失敗させず、壊れた値を正常な値へ丸めない。クエリそのものの失敗は全体を失敗させる。ページの目印は、返せた件数ではなく走査した候補の境界で決める。作業待ちの行を読むのは手順の口で、黙って除かない。

## テスト：実物の PostgreSQL で、資料の After と突き合わせる

永続化層のテストが主に担うのは、`Then:` が記録される行、DB の制約が守る拒否、同時に起きたときの結果を観測するコマンドデータモデルの BDD と、取得結果を観測するクエリデータモデルの BDD である。集約が拒むものは、コマンドデータモデルに「記録されない」BDD として載っていてもドメインのテストが主に担う。

When は、Find で得た実物の集約のコマンドと実物の Apply で起こし、イベントを直接組み立てない。Before は持ち主の書き込み経路で作り、時刻と識別子は mock に資料の値を返させ、資料の識別子（`L-001`）は名前を付けた固定の UUID の `const` に対応させる。コマンドデータモデルが After に挙げたテーブルは全行と全列を突き合わせ、挙げていないテーブルは DB のカタログから取って行数が変わらないことを確かめる。資料にテーブルを足さなくても、意図しない書き込みを見つけるためである。Before に無いテーブルに前提の行が要ると気付いたら、テストで辻褄を合わせずに資料へ提案する。行を読むテスト専用の SQL は、本番と別の生成の package に置く。

同時に起きたときの BDD は、goroutine を並べずに、一つのテストの中で二つのトランザクションを決めた順に進めて起こす。どちらも材料を読み終えるところまで進め、一つ目を確定させてから二つ目の書き込みと確定を行う。一つ目の確定の前に二つ目で同じ行へ書くと、ロックを待って先へ進めなくなる。版の衝突は、古い版の集約を `Restore*` で持ったまま先に新しい版を記録し、その後に古い版の結果を Apply して起こす。

資料に無いケースとして、Find が状態ごとに正しい型を返すこと、初期状態の型の Find が外の事実を正しく読むこと、行が無い、保存値が壊れている、ctx にトランザクションが無い、を足す。Query の実装は、クエリデータモデルの Before を作って読み取りのポートを呼び、取得結果を `assert.Equal` で突き合わせ、絞り込み、並び、ページ、空、壊れた一件を除くことを確かめる。

## 止まるとき

資料に無いテーブル、列、制約、読み取りが要るとき、並行実行の保証がコマンドデータモデルにあるのに物理設計に守り方の指定が無いとき、コマンドデータモデルの BDD に Before と After の表が、クエリデータモデルの BDD に Before と取得結果の表が無いとき、前提を持ち主の書き込み経路で作れないとき、interface に無いメソッド（一覧、件数、存在の確認）が要るときは、書かずに資料か持ち主へ返す。query や変換の関数の名前の揺れでは止まらない。報告には、メソッドごとに読み書きするテーブル、時点の出どころ、翻訳の対応、読み取りの一覧との対応、テストが主に担う BDD の ID を書く。
