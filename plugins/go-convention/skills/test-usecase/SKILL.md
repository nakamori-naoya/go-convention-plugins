# test-usecase

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

usecase が部品を正しく配線していることを、実物を通して確かめる。読み終えると、usecase のテストで何を確かめ、何をほかの層に任せるかを決められる。

中心にあるのは一つの考えである。**usecase のテストは、配線と境界だけを確かめる。** usecase は判断を持たないので、判断の網羅はここに無い。確かめるのは、正しい部品を、正しいトランザクションの区切りで、正しい順に呼んでいることである。

テストの形、実 DB の基盤、テストデータ、差し替えてよい境界、BDD の写し方は、apply-go-test-convention に従う。

## 入力

対象の usecase と、その形（command、手順、query）、業務知識とデータモデルと物理設計の資料の絶対 path を受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

テストを書く場面は二つあり、どちらも通常である。テストが先の場面では、資料と implement-usecase の形から名前とシグネチャを決めて書く。そのテストが赤かどうかは、development-convention の `develop-inside-out` の赤の定義で判断する。

## 判断基準

### 何を確かめるか

command では、配線と保存、トランザクションの境界、拒否の伝わり方、業務の時刻と識別子を確かめる。同時に起きたときのやり直しは、実行順に頼らずには再現できないので、ここでは確かめない。手順では、一件ごとの確定、外部との通信の位置、失敗の扱い、冪等の鍵を確かめる。入力の検証、拒否の理由の網羅、行の全列、Code と認可、ログは確かめない。usecase のテストが主に担う BDD（複数の書き込みが同じ確定で起きる、手順の順序）は、資料の ID で写す。詳しくは [何をテストするか](references/what-to-test.md) を読む。

### どう組み立てるか

実物の DB、リポジトリ、Query の実装、トランザクションの管理を、本番と同じコンストラクタで組み、時計と採番器と外部の境界のポートだけを gomock で差し替える。前提は持ち主の書き込み経路で作る。観測は、観点が見るテーブルと返り値だけにする。詳しくは [実物で通す](references/setup.md) を読む。

## 手順

1. **対象と観点を決める。** `references` があれば先に読む。usecase の形と、確かめる観点を並べる。usecase のテストが主に担う BDD を拾う。
2. **表を書く。** 観点ごとにケースを置き、前提を作る Builder、入力、期待の返り値、観点が見るテーブルの期待を並べる。
3. **ループ本体を書く。** 前提を作る → 本番と同じコンストラクタで組む → `Execute` → 返り値を確かめる → 観点のテーブルを読んで確かめる、を一回書く。
4. **機械検査を通す。** テストが先の場面で `go vet` と `go test` が失敗したら、それが赤か停止かを `develop-inside-out` の赤の定義で判断する。
   ```bash
   go vet ./...
   go test -count=1 ./<usecase package>/...
   ```
   テストの形の検査と、repository 全体の BDD の網羅の検査は、apply-go-test-convention の tool で行う。
5. **報告する。** 出力の項目を返す。

## 停止条件

トランザクションの境界の途中の失敗を、実物を壊れた状態にして起こせないときは、偽物で代用せずに、制約の不足を物理設計の資料へ返す。前提を持ち主の書き込み経路で作れないときは、書き込み経路の不足を返す。usecase が判断を持っていて、判断の網羅がここに要ると感じたら、それは usecase の規約違反なので implement-usecase へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

## 出力

対象の usecase とテスト関数、確かめた観点と書かなかった観点（任せた層）、主に担う BDD の ID、途中の失敗を起こした方法、差し替えた境界、機械検査の結果、返した論点を報告する。

機械検査が通って言えるのは、実物の上で全ケースが通ったことと、テストの形と BDD の網羅の構造だけである。観点が配線を正しく確かめているかは、対象を読んで報告する。
