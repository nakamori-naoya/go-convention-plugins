# 何をテストするか

usecase のテストは、usecase が部品を正しく配線していることを、実物の DB、実物のリポジトリ、実物のトランザクションの管理を通して、DB の状態と返り値で確かめる。業務の判断はドメインのテストが、行の形と DB の制約は永続化層のテストが、変換と Code と認可は API のテストが確かめているので、ここでは繰り返さない。

# 主に担う BDD

usecase のテストが主に担うのは、`Then:` が、複数の書き込みが同じ確定で起きること、手順の順序、手順の一件ごとの確定を観測する BDD である。図書館では、「延滞になり、通知の要求が同じ変更で積まれる」がこれに当たる。これらは資料の ID で写す（apply-go-test-convention）。

# 戦術的 DDD の command で確かめること

**配線と保存。** 見つける、呼ぶ、適用するを通って、コマンドの結果が保存されること。一つの代表的なケースで、保存された行を確かめる。行の全列の網羅は、永続化層のテストに任せる。

**トランザクションの境界。** 一つの確定に入るべき書き込み（延滞と通知の要求）が、両方そろって確定すること。途中の書き込みが失敗したら、先の書き込みも残らないこと。途中の失敗は、実物を壊れた状態にして起こす（先に同じ版を記録しておき、後の書き込みを一意制約の違反にする）。偽のリポジトリで失敗を返させない。

**拒否の伝わり方。** コマンドが拒んだら、usecase が何も保存せずに、その具体エラーを返すこと。拒否の理由ごとの網羅は、ドメインのテストに任せる。一つの代表的な拒否で足りる。

**業務の時刻と識別子。** 入力の業務の時刻が、そのまま保存されること。採番器が返した識別子が、出力と保存に使われること。

**物理設計の指定は確かめない。** 一つの usecase の中のトランザクションに、別のトランザクションを決めた順で割り込ませることはできない。goroutine の実行順に頼れば、同じ結果を安定して再現できない。直列化の失敗を指定した回数だけやり直すことはトランザクションの管理のテストが、同時に起きたときの結果は永続化層のテストが、それぞれ順に再現して確かめる。

# 単純なパターンの手順で確かめること

**一件ごとの確定。** 途中の一件が失敗しても、それより前に確定した件が残ること。

**外部との通信の位置。** 外部へ送るポートの mock（gomock）が呼ばれた時点で、その件を回収した記録が確定していること。外部への通信がトランザクションの中で行われていないこと。

**失敗の扱い。** 外部へ送るポートが、その一件だけに関わる失敗を返したら、次の件へ進むこと。全体に及ぶ失敗を返したら、残りを試さずに返すこと。再処理で通らない失敗なら、恒久失敗が記録されること。

**冪等の鍵。** 外部へ送るポートに、重複した送信を相手が見分ける鍵として、要求の識別子が渡ること。

# 確かめないこと

入力の値オブジェクトの検証（入口と値オブジェクトのテスト）、拒否の理由の網羅（ドメインのテスト）、行の全列と制約の翻訳（永続化層のテスト）、Code と公開の文言と認可（API のテスト）、ログが出たか、は確かめない。
