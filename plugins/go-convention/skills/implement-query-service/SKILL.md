# implement-query-service

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

読み取りのポートの RDB 実装を、SQL の射影と集計と、必要な値オブジェクトか純関数の業務の計算から組み立てる。読み終えると、どの接続から、どの SQL で読み、壊れた一件をどう扱うかを決められる。

中心にあるのは二つの考えである。一つは、**読み取りは読み取り専用の接続だけから読む**ことである。トランザクションの有無で読み方を切り替えない。もう一つは、**一件の壊れた値で一覧全体を止めない**ことである。

## 入力

usecase の側が所有する読み取りのポートと読み取りモデル、物理設計の資料の読み取りの台帳、データモデルの資料の絶対 path を受け取る。借りる値オブジェクトか純関数があれば、その根拠も受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。

先に赤いテストがある場面も通常である。テストが前提にするコンストラクタとポートに合わせ、テストを変えずに緑にする実装を書く。

## 判断基準

読み取り専用の接続だけから読み、書き込みを型で拒む executor を使う。ctx のトランザクションを見ない。トランザクションを張らず、集約を復元しない。SQL は台帳にあるものだけにする。SQL で書けない業務の計算は、値オブジェクトか純関数を借りる。互いに独立した複数件を返すなら、壊れた一件だけを除いて ERROR で記録し、残りを返す。詳しくは [Query の実装](references/query-service.md) を読む。

## 手順

1. **契約と台帳を確かめる。** `references` があれば先に読む。読み取りのポートの各フィールドの意味と、物理設計の読み取りの台帳の対応する Read を並べる。
2. **SQL を書く。** 台帳の Read ごとに SQL を書き、`sqlc generate` で生成する。
3. **読み取りモデルを組み立てる。** 行を値オブジェクトへ戻し、業務の計算を借りて、読み取りモデルにする。壊れた一件の扱いを置く。
4. **Query の型を書く。** 読み取り専用の接続と logger を受け取り、ポートを満たす。
5. **機械検査を通す。**
   ```bash
   sqlc generate && git diff --exit-code -- '*/sqlcgen/*'
   go build ./... && go vet ./...
   go tool golangci-lint run ./...
   ```
6. **報告する。** 出力の項目を返す。

## 停止条件

台帳に無い読み取りが要るときは、足さずに物理設計の資料へ返す。読み取りのポートやモデルが契約として決まっていないときは、implement-usecase と apply-go-package-layout へ返す。SQL で書けない業務の計算の根拠が資料に無いときは、推測で計算せずに資料へ返す。集約の復元や書き込みが要ると判断したら、それは読み取りではないので、apply-layer-convention へ返す。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

## 出力

実装したポートと、台帳の Read との対応、借りた値オブジェクトか純関数、壊れた一件の扱い、返した論点、機械検査の結果を報告する。

機械検査が通って言えるのは、生成物が SQL と一致し、ビルドと vet と linter に違反が無いことだけである。読み取りモデルが資料の期待と一致するかは、test-repository のテストで確かめる。
