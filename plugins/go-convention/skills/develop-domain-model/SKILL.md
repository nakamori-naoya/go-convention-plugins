# develop-domain-model

中心にあるのは二つの考えである。**業務の操作を受けるか拒むかはコマンドが決め、値と状態が資料の意味を満たすことはそれを作る入口が守る。** 値オブジェクトも集約の状態も、成立に必要な材料を一つの生成入口で揃え、成功時には完全な値だけを返す。生成・遷移・復元で成立条件を変えず、部分的な値を後から setter で完成させない。型の名前や非公開フィールドだけでは、その条件を満たした証拠にならない。初期状態を含め、コマンドは判断する状態の型のメソッドにし、その型が判断の材料を持つ。そうすれば usecase は、集約を見つけ、コマンドを一回呼び、結果を適用するだけで書ける。**資料が決め、コードはそれを写す。** 欠けた資料が結論を変える単位は書かずに持ち主へ返し、独立して決まる単位は進める。

この一単位では、ドメインの業務判断をメモリ上のテストで先に赤にする。development-convention の `develop-inside-out` は一単位の赤とTDDの順序に限って参照し、APIテストシナリオを起点とする全層の手順はこの二資料だけの作業の前提にしない。言語の形は write-go-code、エラーは handle-errors、テストの共通の形は apply-go-test-convention に従う。公開APIや実DBを通す実装は、この二資料だけの完成条件に含めない。名前、状態、コマンド、拒む理由は対象の資料から決める。

## 資料をどう読むか

業務入力は業務知識とドメインモデルの二資料である。ドメインモデルは境界、判断の持ち主、重要な値の関係を議論した叩き台として読む。`<<集約ルート>>` などの種別は型の候補を示すが、図を実装型の一覧とせず、すべての要素、コマンド、引数、状態遷移があるとも仮定しない。実装する行い、その条件と拒む理由、次状態、イベントの業務上の意味は業務知識のBDDと規則から読み、ドメインモデルが割り当てた判断の持ち主と照合する。業務上のイベントを返すことと、イベントの値を履歴へどう保存するかは別の判断である。ドメインモデルの採用案と業務知識が食い違うなら、どちらかを黙って修正せず持ち主へ返す。業務知識に無い拒む理由は作らない。

コマンドの引数のうち、集約の外の事実の写しとそれを読む識別子は、判断する状態の型が持つ。外の事実は保存された集約の値と区別し、次のコマンドで使うときはその時点の値に更新する。取得方法と Find の形は保存契約が決まるまで確定せず、ドメインのテストでは必要な判断材料を完全な値として渡す。二資料で発行する ID が必要と決まっていれば、発行済みの ID をメソッドの引数に残す。時刻を引数と状態に置くかは development-convention の `apply-layer-convention` の基準で決め、置く時刻は日付ではなく時点の値オブジェクトで受ける。時点を暦へ変えるタイムゾーンのような設定値は、それを持つ値オブジェクトを組み立ての場所が一度だけ作って引数で渡し、ドメインは既定のタイムゾーンを読まない。材料の要らない生成では Find を置かず、usecase が初期状態の型を作る。

提案の段階のもの（ドメインモデルが業務知識への提案に回したもの）と未決のものは写さない。保存した集約を見分ける識別子を含め、二資料で識別子や業務上の意味が未決なら仮置きしてコードで決めず、その影響を受ける単位だけを持ち主へ返す。資料に無い業務上の状態や行いは足さない。完全な状態を作るための非公開の初期型や中間表現、`Restore<状態名>`、呼び手がいる値の取り出しの関数、コマンドの結果の型は実装上の形として置ける。初期型を保存後も再開できる業務上の下書きとして扱うなら、その意味は業務知識の持ち主へ返す。

## 集約の形

まず業務上の可否が値だけで決まる条件を値オブジェクトへ置く。状態遷移後に受ける行い・拒む理由・次状態が変わる集約では、その違いを状態別の型で表す。状態ごとに判断が変わらない集約へ状態型を増やさない。状態別に表す場合、まだ保存されていない集約は**初期状態の型**で表し、版を持たせない。共通の struct や interface を通しても版を持ち込まず、版0のような特別な値を作らない。保存されていないことを型が表すからである。判断材料がある初期状態は具象型を非公開にし、`New*` が必要な値を揃えて作る。材料が無ければ空の型で足りる。保存された状態の版は、別の保存契約がその集約の版を要求するときだけ持つ。業務知識とドメインモデルから版を推測しない。図の終端が保存される状態かどうかは資料が決める。

状態別の型を使うとき、保存された状態の型の和は、非公開のメソッドを一つ持つ interface で閉じ、`//sumtype:decl` を付ける。**和型は、保存された状態が受けうるすべてのコマンドを持つ。** 具象の保存状態を非公開にし、完全に組み立てた値だけを和型で返す。新しい実装を外から足せないだけでなく、外から保存状態のゼロ値を作って復元時の不変条件を迂回できない公開面にする。受けるか拒むかは状態ごとの型が決め、受けない状態は資料の拒む理由を返す。こうすると usecase は状態を調べずにコマンドを呼べ、コマンドを足すと全部の状態で決めるまでコンパイルが通らない。受けない状態の拒む理由が資料に無ければ、そのコマンドは和型に置かず、それを使う usecase も書かずに資料へ返す。どの状態でも変わらない値は、業務の言葉で名付けた非公開の struct にまとめて埋め込み、同じ振る舞いは非公開の関数に一つだけ書く。

生成と保存済み状態からの遷移を一つのコマンドが兼ねる集約では、初期状態の型も和型に入れる。行の有無によってコマンドを受けるか拒むかは状態の型が決め、呼び手に業務判断を漏らさない。Find が行を見つけないときに返す型と復元の形は、永続化ポートを定める保存契約が確定したときに決める。

コマンドは判断を持つ集約の値レシーバのメソッドで、結果と error を返す。状態別の型を使う場合は各状態のメソッドとする。結果は業務知識にある次状態と業務イベントを表し、保存型や履歴への書き込みを決めない。次状態をそのまま次のコマンドへ使うなら判断材料を欠かさず、外の事実が変わる場合は次のコマンドの前に取り直す。別の保存契約が版を要求するときだけ、その契約が決める版の進め方と初期値に従う。事前条件は資料の順に確かめて最初に破れた理由を返し、順が決まっていなければ仮置きして報告する。状態別の型が「〜の状態である」を表すときは同じ条件を `if` で重ねない。拒まないが何も変えないことがあるコマンドは `(Result, bool)` を返す。判断だけの公開メソッドは置かない。呼ぶ側が先に判断する形は、業務の判断を usecase へ漏らすからである。コマンドの事前条件はコマンドが判断し、状態の必須値と関係は非公開の生成入口で守る。コマンドの次状態は同じ成立条件を通して完全な状態だけを返す。保存契約が確定して復元が要る場合は `Restore<状態名>` も同じ成立条件を通し、保存値だけで判定できない外部の事実を再判定しない。ドメインは時計を持たず ID の発行もせず、業務の数は非公開の定数にする。

## 値オブジェクト、イベント、保存契約があるときの永続化ポート

値オブジェクトは非公開フィールドの struct を `New*` だけが必要な値を一度に受けて作り、値が一つでも `struct{ v string }` にする。拒む値があるときだけ `(X, error)` を返し、生成の中で正規化して（時点は `UTC()`）`==` で比べられる値にする。Go では公開された値型のゼロ値も渡せるので、集約の生成入口とコマンドは受け取った値が必須条件を満たすか確かめ、`New*` を経たはずだと仮定しない。`String()`、`LogValuer`、`MarshalJSON`、`Scan`、`Validate()` を実装しない。何を外へ出すかは、記録や変換をする行で決めるからである。二資料で必要と決まった識別子は型ごとに別の struct にし、ID ジェネレーターが UUID を発行する契約ならその場で変換する関数を置く。「〜から決まる値」は材料を受けて `New*` の中で決める。

イベントは業務知識のイベント一つに型一つで、業務結果を観測するために必要な値を二資料から決める。名前は確定した業務の英名を使い、クラス図に英名が無ければ図から補わない。時刻は同じ基準でコマンドが判断に使った時点だけを持つ。保存用の値と版は別の保存契約が要求するときに決め、取り出しの関数は呼び手が読むものだけにし、生成関数を公開しない。永続化ポートは保存型と書き込みの契約が確定したときだけ集約と同じ package に置き、完全な集約を返す `Find<返す型>` と、その保存型に合う書き込みのメソッドを持たせる。イベント履歴を保存する契約なら `Apply<イベント名>` は error だけを返す。リソース中心の契約なら定められた現在の値を保存し、イベント表を要求しない。ドメインは `log/slog`、pgx、connect、JSON を import しない。

## テスト：判断だけを、メモリの上の値で確かめる

ドメインのテストが主に担うのは、`Then:` が、受けるか拒むか、次の状態、発するイベント、値の生成の条件を観測する BDD である。DB の制約が守る拒否と同時に起きたときは永続化の、本人の確認は入口のテストが主に担う。テスト関数は、値オブジェクトならその生成条件、集約のコマンドなら判断を持つ型とコマンドを名前にする。状態別の和型を使う場合は状態の型ごとの `Test<状態の型>_<コマンド>` にし、受けない状態のテストにその状態で拒む BDD を置く。

Given は初期状態と `New*` に渡す値で、資料の `Given:` に現れないが確定した識別子は表の前で一度だけ作る。When はコマンドの引数、Then は資料どおりの次状態をメモリ上で完全に組んだ `wantNext`、イベントから取り出した業務結果の値を並べた `wantEvent`、`wantErr` である。次状態から続く操作も通して、単発のコマンドだけでは見えない欠落を見つける。保存契約が確定して `Restore*` を設けた場合に限り、契約が要求する版を表の前で作り、生成直後と復元後の両経路で同じ不変条件を確かめる。資料に無いケースは、具体エラーごと、境界の両側、理由を同時に破る組の順、`false` の側を足したら止める。値を取り出すだけのテストは書かない。資源を持たないので `t.Parallel()` をテスト関数とサブテストの両方に置く。

## 機械検査と止まるとき

```bash
gofmt -l ./<domain package>
go vet ./<domain package>/...
go tool golangci-lint run ./<domain package>/...
go test -shuffle=on -count=1 ./<domain package>/...
```

受けない状態の拒む理由、業務コマンド、次状態、業務イベントの結果に未決があり、その欠落で結論が変わる単位は書かずに業務知識の持ち主へ返す。保存型や版だけが未決なら、二資料で決まるドメイン判断とメモリ上のテストを進め、永続化ポートと保存値だけを保留する。提案の段階のもの、判断に要る時刻を時点で受けられないものも、影響を受ける単位だけ保留する。名前で止まるかは development-convention の `write-readable-code` の基準に従う。事前条件の順では止まらず、仮説を採って報告に示す。報告には、二資料と型の対応、止めたものと返し先、保存契約を待つもの、主に担う BDD の ID を書く。
