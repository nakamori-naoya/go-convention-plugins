# develop-domain-model

[工程順序の正本](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と、`skill:` 工程が指す入口の本文を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

これは、**ドメイン層の 1 単位を「テストを書く → 赤を確かめる → 実装する → 緑を確かめる → 整える」の順で完成させる合成の入口**である。1 単位は、domain-model 資料の「BDDとの対応」表が 1 つの要素（集約・値オブジェクト）に割り振る BDD と、その要素の操作の集合である。テスト file（`*_test.go`）と実装 file は分かれたままで、この入口は両者を交互に書く順序と、その間の判断だけを持つ。

これは、**テストの書き方や実装の形を新たに決めるものではない**。何をテストし、どう表に写すかはドメインのテストの規約が、資料をどう型・メソッド・sentinel に写すかはドメインの実装の規約が、言語レベルの形は言語規約が、sentinel の定義と文言はエラーの規約が持つ。それぞれは `playbook.yml` の `skill:` 工程が指し、この入口はそれらを変えない。永続化（復元の往復・DB 制約）、usecase の手順、RPC の入口は別の単位の入口が扱う。

前提: Go 1.27・testify。ドメイン層は DB・コンテナ・モック・スタブを使わない。

## 入力

- domain-model 資料（「BDDとの対応」表を持つ）の絶対pathと、この単位で完成させる要素（集約 1 つ、または値オブジェクト 1 つ）。
- 対象のドメイン package のpath。既存のcodeとテストがあればそのpath。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

## 判断基準（TDD の 1 単位）

| 観察対象 | 述語 |
|---|---|
| 赤の理由 | `run-red` で対象のテスト関数が失敗し、その理由が「対象の型・関数・メソッド・sentinel がまだ無い（コンパイルエラー）」か「操作が資料の結果を返さない（assert の失敗）」のどちらかに分類できる。無関係な既存テストの失敗、テストの形の違反、環境の不備は赤ではない |
| 実装中のテスト | `implement` の間、`*_test.go` を編集していない。テストの誤りに気付いたら実装を止め、`write-failing-test` へ戻って直し、赤を確かめ直してから実装へ進む |
| 緑の範囲 | `run-green` で、対象のテスト関数と同じ package の全テストが通り、ドメインのテストの規約が求める機械検査（`go vet`・`-shuffle=on`・単独実行・BDD 網羅）も通る |
| 整える前後 | `refactor` の前後で同じテストが緑で、テストの `id` / `name` / `description` と `want*` を変えていない。振る舞いを変える必要が見つかったら、それは次の単位のテストから始める |
| テストの範囲 | テストのケースは、資料の BDD と、ドメインのテストの規約が定める派生（sentinel ごと・事前条件の順・境界・`(Result, bool)` の false 側）だけ。資料に無い操作・状態・拒む理由を、テストから先に作らない |
| 単位の大きさ | 1 サイクルで完成させるのは 1 要素。資料の別の要素に手を伸ばす必要が出たら、この単位を緑で閉じてから次の単位を始める |

## 手順

1. **単位を固定する（`fix-unit`）。** `references` があれば先に読む。domain-model 資料の「BDDとの対応」表から、この単位の要素と、それに割り振られた BDD・操作を列挙する。テスト file と実装 file の名前を決め、既存なら現在の `go test ./<package>/...` の結果（通る／通らない、失敗している関数）を記録する。完了条件: 要素 1 つ、BDD の ID 一覧、この単位が公開する API の名前とシグネチャ（生成関数・状態型のメソッド・sentinel。実装の規約の命名で資料の行と 1:1）、テスト file と実装 file のpath、開始時のテスト結果が 1 行ずつ言える
2. **テストを書く（`write-failing-test`）。** ドメインのテストの規約に、資料と単位（要素、BDD、API の名前とシグネチャ、sentinel）を渡し、テストが先の場面として適用する。その規約が返すのは、資料の BDD を写したテスト file と、対象未実装による赤の記録である。完了条件: この単位の BDD が `id:` か末尾コメントに現れ、テスト file が保存され、`go test` の失敗理由が記録されている
3. **赤を確かめる（`run-red`）。** `go test -count=1 -run '<テスト関数>' ./<package>/...` を実行し、失敗の理由を上の表で分類する。完了条件: 失敗の理由が「対象未実装」または「資料の結果を返さない」で、それ以外の失敗が無い
   ```bash
   go test -count=1 -run 'TestHold' ./reservation/...          # 対象のテスト関数だけ
   ```
4. **実装する（`implement`）。** ドメインの実装の規約に従い、資料の要素・操作・拒む理由を型・メソッド・sentinel に写す。テストが緑になる最小の実装を書き、`*_test.go` は触らない。完了条件: 資料の全行に対応する Go の名前があり、テストの `want*` に現れる値・sentinel が実装に存在する
5. **緑を確かめる（`run-green`）。** 対象のテスト関数、同じ package の全テスト、ドメインのテストの規約の機械検査をすべて通す。完了条件: 次が全部通る
   ```bash
   go vet ./<package>/...
   go test -shuffle=on -count=1 ./<package>/...
   go test -count=1 -run '<テスト関数>/<id>_' ./<package>/...   # 足したケースを 1 つずつ単独で
   ```
   続けて、ドメインのテストの規約が持つ機械検査（BDD 網羅・ケース識別）を同じディレクトリに対して通す
6. **整える（`refactor`）。** 言語規約で関数の形・型と interface・名前・標準ライブラリを揃える。振る舞いは変えず、テストは触らない。完了条件: 言語規約の機械検査（gofmt / goimports / vet / golangci-lint / `go test -race -shuffle=on`）が通り、手順 5 と同じテストが緑
7. **エラーを揃える（`align-errors`。この単位で sentinel を足した・文言を変えたときだけ）。** エラーの規約で、資料の「拒む理由」と 1:1 の sentinel と文言を揃える。完了条件: sentinel のブロックが資料の語と 1:1 で、テストが緑
8. **報告する（`report`）。** 下の「報告」の項目

## 停止条件

止まるのは、資料または規約の契約に反する要求、正本に無い決定が要る、利用者の許可が要る、toolが失敗した、のどれかに当たるときで、それ以外の判断の揺れでは止まらない。

- `run-red` で対象のテストが最初から緑 → 対象が実装済みか、テストが資料を写していない。実装へ進まず、どちらかを確かめてテストの工程へ戻る
- `run-red` の失敗理由が対象未実装以外（無関係なテストの失敗、`go.mod` の版、テストの形の違反）→ 実装へ進まない。理由を返して止まる
- `run-green` で緑にならず、原因がテストの誤り → 実装を止め、`write-failing-test` へ戻って直し、`run-red` からやり直す（これは停止ではなく戻り）
- `run-green` で緑にならず、原因が資料の矛盾（BDD の期待が実装の規約で表せない）→ 止まり、資料のどの行かを返す
- 各 `skill:` 工程が持つ停止条件に当たった → その工程の報告に従って止まる

止まるときは、書いた範囲（テスト file・実装 file）と書かなかった範囲を分け、どの工程で止まったか、返す先（資料、規約、利用者）と必要な決定を報告に示す。

判断の揺れでは、その時点の根拠から最も筋の良い形を仮説として採り、仮説であることと採らなかった形を報告に明示して進む。

- 単位の切り方が資料から一意に決まらない（集約と、それが使う VO を同じ単位にするか）: VO を先に単独の単位として閉じ、集約を次の単位にする形を採り、報告に示す。

## 報告

- 単位（要素、BDD の ID 一覧、テスト file と実装 file）
- 赤の理由（コンパイルエラー／assert の失敗と、その対象）と、緑になった時点の機械検査の結果
- 整えた点（言語規約・エラーの規約で変えたもの）と、振る舞いを変えていないことの根拠（同じテストの緑）
- 各 `skill:` 工程の報告
- 停止条件に当たって返した論点、次の単位の候補
