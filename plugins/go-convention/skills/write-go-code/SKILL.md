# write-go-code

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

## 目的

Go 1.27 のコードを、どの層でも同じ言語レベルの形で書く。読み終えると、関数・型・名前・コメント・標準ライブラリ・ツールの形を、一つの答えに揃えられる。

この規約が守るものは二つである。一つは、**失敗を隠さず、原因の行を読み手の近くに置く**ことである。値を丸めたり、フォールバックしたり、暗黙に初期化したりすると、失敗の痕跡が消え、別の場所で「なぜかこの値」として現れる。もう一つは、**型が業務の意味を運ぶ**ことである。業務の概念を `string` や `int` のまま運ぶと、取り違えをコンパイラが止められず、検証が散らばる。

何を作るか（集約の構造、永続化、usecase の手順、RPC などの要求を受ける入口、エラーの分類、ログの置き場、テスト）は、それぞれを担当する skill が決める。この規約は、それらが共通に載る言語の土台である。

## 入力

書く・直す対象の package と型・関数、その層を受け取る。既存のコードとテストがあれば、その path も受け取る。

`references` は任意で、追加で従う資料の絶対 path の配列である。手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象 repository の AGENTS.md / CLAUDE.md と `references` で渡される。この skill は既定値を持たない。

前提は Go 1.27（`go.mod` の `go 1.27`）である。標準ライブラリを優先し、外部依存は層別の規約が指定するものと、`golang.org/x/sync/errgroup`、`golang.org/x/tools`（goimports）、golangci-lint v2 だけにする。

## 判断基準

### 業務の概念はプリミティブ型で運ばない

構造体のフィールド、引数と戻り値、イベント、usecase の入出力、読み取りモデル、テストデータのどこでも、業務や運用の意味を持つ値を `string`、整数、浮動小数、`bool`、`time.Time` のまま持たない。値オブジェクト（非公開フィールドの struct と、検証する `New*`）にする。取りうる値が有限なら、封じた型（非公開フィールドの struct と package 変数）にする。外から入ってくる値（要求、外部サービスの応答、設定）は、境界で値オブジェクトへ変換し、応答を写した型も例外にしない。逆向きに、外へ出す写しとしてプリミティブへ戻すのは、外部の形式（DB の生成型、proto、ログの属性）へ写す変換の内側だけである。

設定値も同じである。環境変数は名前付きの型で受け、読み込みの時点で検証し、内側へは値オブジェクトで渡す。新しく型を作る前に、同じ意味の型が既にないかを探す。詳しくは [型と interface](references/types-and-interfaces.md) を読む。

### 未知の値を丸めず、フォールバックを書かない

受け取った値が条件を満たさなければ、既定値に丸めずに error を返す。`switch` は取りうる値をすべて列挙し、残りは error で返す。`map` を引けなかったときも同じである。一次手段が失敗したら別の手段で黙って続ける、というフォールバックは書かない。フォールバックが要ると判断したら、書く前に止まって利用者の許可を得る。

トランザクションが要る場面で、トランザクションが無ければ pool で続ける、という切り替えもフォールバックである。書かない。詳しくは [基本](references/basics.md) を読む。

資料が曖昧なときに止まって提案するという、言語に依らない規律は develop-inside-out が持つ。この規約が持つのは、それを Go でどう書くかである。

### 関数の形を一つに揃える

分岐はガード節で書き、本筋を字下げ無しで最後に置く。返り値は `(T, error)` か `(T, bool)` か一つで、それを超えるなら結果の struct を返す。naked return は書かない。`context.Context` は、I/O をする関数と、それを呼ぶ関数の第一引数にだけ置き、struct に持たない。値渡しを既定にし、ポインタは状態を変える協力者と、nil が意味を持つ引数だけにする。`init` を書かず、`main` は `run(ctx) error` を呼ぶ。いまの呼び出しが要らない関数・引数・分岐は書かない。詳しくは [基本](references/basics.md) を読む。

### interface は使う側で小さく切る

interface は、それを引数に取る package が、呼ぶメソッドだけを持つ形で定義する。例外は二つで、集約の永続化ポートと状態の和型はドメインが定義し、差し替えるためだけにある技術境界（時計、採番器）の interface は、それを所有する横断的関心事の package に一つだけ置く。interface と、それを実装する型は、別のファイルに置く。詳しくは [型と interface](references/types-and-interfaces.md) を読む。

### 名前とコメントは呼び出し側で読まれる

名前は `package.Name` の形で読んだときに、一回で意味が通るように付ける。コメントは、コードから分からないこと（業務上の意味、似た概念との違い、不変条件、シグネチャから読めない契約）だけを、その型や関数自身の責務の範囲で、業務の言葉で書く。外部の値には実際の値のサンプルを一つ添える。詳しくは [命名](references/naming.md) と [コメント](references/comments.md) を読む。

### 標準ライブラリとツールに任せる

標準ライブラリで書けるものは、標準ライブラリで書く。書き換えの多くは `go fix ./...` の modernizer が機械で行うので、先に走らせる。[標準ライブラリ](references/stdlib-1.27.md) は、`go fix` の後に残ったものを直すときに読む。機械で言えること（フォーマット、import 順、禁止 API、網羅）は、ツールが落とす状態にする（[ツール](references/tooling.md)）。

## 手順

1. **対象と層を決める。** `references` があれば先に読む。書く・直すファイルと、それぞれの層を言う。層に固有の形は層別の skill に従い、ここでは言語レベルだけを見る。
2. **`go.mod` とツールを確かめる。** `go 1.27`、`tool` directive、`.golangci.yml` が [ツール](references/tooling.md) の形になっているかを見る。無ければ先に整える。
3. **型を揃える。** プリミティブで運んでいる業務の概念と設定値を、値オブジェクトか封じた型にする。interface の置き場とファイルの分け方を揃える。
4. **関数の形を揃える。** ガード節、返り値、ctx、引数、値とポインタ、レシーバを揃える。丸めとフォールバックを見つけたら消し、error を返す形にする。
5. **名前とコメントを揃える。** 名前を [命名](references/naming.md) に、コメントを [コメント](references/comments.md) に合わせる。
6. **標準ライブラリに置き換える。** `go fix ./...` を先に走らせ、残りを手で直す。同じ module に既にある関数を再実装していないかも見る。
7. **機械検査を通す。** `gofmt -l .` と `go tool goimports -local <module path> -l .` が空で、`go vet ./...`、`go tool golangci-lint run ./...`、`go test -race -shuffle=on -count=1 ./...` が通る。
8. **報告する。** 出力の項目を返す。

## 停止条件

次のときは、書かずに止まる。

フォールバックが要ると判断したときは、一次手段、失敗の条件、代替手段、続行したときに隠れる失敗を示し、利用者の許可を得てから書く。既定値への丸めが資料に「仕様」として書いてあるときは、資料のその箇所を示し、error を返す形にできないかを資料の持ち主へ確かめる。前提に無い外部依存が要ると判断したときは、標準ライブラリと既存の依存で書けない理由、候補と版、背負うもの（更新、脆弱性）を示し、許可を得てから足す。`go.mod` を `go 1.27` へ上げられないときは、書かない。対象が生成コードなら直さず、生成元（SQL、proto）を直すことを提案する。

止まるときは、書いた範囲と書かなかった範囲を分け、返す先と必要な決定を報告に示す。

設計の揺れ（名前、分割、定義の場所）では止まらない。最も筋の良い形を仮説として採り、仮説であることと採らなかった形を報告に示して進む。

## 出力

対象のファイルと層、直したシグネチャ（前と後）と根拠の節、型にした概念と設定値、消した丸めとフォールバックと代わりに返す error、置き換えた標準ライブラリ（`go fix` が直した分と手で直した分）、機械検査の結果、止まって返した論点と返し先を報告する。

機械検査が通って言えるのは、フォーマット、import 順、vet の検査、linter の検査（naked return、ctx の欠落、禁止 API、import の禁止、和型の網羅）、`go fix` の modernizer に違反が無いことだけである。プリミティブで運んでいないこと、丸めとフォールバックが無いこと、interface の置き場、コメントの中身は、機械では言えないので、対象を読んで報告する。
