# コメント

コメントは、コードだけでは分からないことを、読み手の判断に足すために書く。足すものが無ければ書かない。

# 書くもの

## コードから分からないことだけを書く

型のコメントには、何の値かに加えて、似た概念との違い、どこで識別や判断に使うか、必要なら実際の値の例を書く。関数やメソッドのコメントは、呼び出し順、トランザクションの境界、エラーの翻訳、秘匿する情報のように、シグネチャから読み取れない契約があるときだけ書く。

識別子やシグネチャを日本語に言い換えただけのコメントは書かない。`NewUserNo` に「UserNo を作る」、`Value` に「値を返す」、変換関数に「A を B へ写す」と書いても、読み手の判断に何も足さない。公開識別子であることだけを理由に、コメントを付けない。関数の本文を上から説明する実況のコメントも書かない。

```go
// Standing は、本を借りる瞬間の利用者の貸出状況である。借りている冊数と、延滞の貸出の有無を持つ。
// 本を借りるコマンドの判断にだけ使い、貸出はこれを持ち続けない。
type Standing struct {
	lent       LentCount
	hasOverdue bool
}
```

## 業務の言葉で書く

値やエラーのコメントには、それが業務上どの条件（値の不変条件、生成の条件、集約の事前条件）に反するのか、どの業務の概念なのかを、業務の言葉で書く。「資料に無い」「言語の都合で置く」「実装の都合」のように、存在の理由を実装や言語の事情に帰する断り書きは書かない。値の構造として必ず拒む値（空の識別子など）なら、それはその値の不変条件である。

## 外部の値には、実際の値のサンプルを一つ添える

外部サービス、環境変数、プロトコルの値を持つフィールドや定数には、実際に来る値のサンプルを一つ添える。説明を長くするより、サンプル一つのほうが伝わる。

```go
// Issuer は、トークンを発行した認証基盤の環境の URL である。例: "https://auth.example-library.jp"。
Issuer IssuerURL

// Procedure は、呼ばれた RPC の完全な名前である。例: "/lending.v1.LoanService/ReturnBook"。
```

# 書かないもの

## 自分の責務だけを書き、使う側の都合を書かない

コメントは、その型や関数自身の目的と責務だけを書く。何を担い、何を担わないかは自分の言葉で閉じ、担わないものを誰が担うかは書かない。使う側の都合（「〜の usecase のポートを満たす」「〜が組み立てで注入する」「〜の handler が呼ぶ」）や、別のディレクトリの型や package の名前を書かない。

使う側の名前を書くと、その使う側が動いたときにコメントが陳腐化する。依存の向きや組み立ては、組み立てる側のコードが示す。

## 陳腐化しない最小の内容にする

ファイルの path、実装の package の名前、手順の詳細を、責務の説明で足りる箇所へ埋め込まない。説明の対象のコードが変わっても古くならない、最小の内容にする。

テストと、テストの前提データを組み立てる Builder のコメントも、同じ基準に従う。既定値がどの BDD の登場人物や状態を表すか、なぜ行を直接入れる必要があるかは書く。表の変数名、期待値、実行手順をそのまま説明するコメントや、別のテストを列挙するコメントは書かない。

## 言語

コメントを書く言語は、対象 repository の規約に従う。
