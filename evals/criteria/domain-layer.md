# ドメイン層の実装に共通する条件

この条件は、実行の担当が develop-domain-model で、業務知識とドメインモデルの資料から、一つの集約をテストと一緒に書いた repository（以下、コード）を判定するためのもので、どのお題にも当てる。ケースに固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しいコードの中身は書かない。どの条件も、ほかの条件の出来では判定しない。

重み3は利用者の原則の芯（業務の言葉、集約は構造体を作ってからコマンドを一回呼ぶ形、判断の材料の置き場、概念にプリミティブを使わない、推測で埋めない、公開するのは使うものだけ、コメントは自分の責務だけ、書く前に書かずに済む道を探す）、重み2は集約とテストの骨組み、重み1は細部である。担当が書いたコードが一つも無いときは、コードを読む条件はすべて FAIL とする。

実行の担当は、`docs/` の二つの資料だけを根拠にするよう指示されていた。資料が提案や未決に回したものは、資料の決まりではない。

## 業務の言葉と、推測で埋めないこと

### naming-business-language

重み: 3

PASS：担当が書いた型、関数、メソッド、package の名前は、資料のユビキタス言語の語（英名があればその英名）から付けられている。資料に英名が無い業務の概念に名前を付けたときは、仮置きであることが報告かコメントで分かる。データや処理の形から付けた名前（組、データ、情報、管理、処理、`Pair`、`Data`、`Info`、`Manager`、`Relationship` の類）と、業務の語があるのに処理の一般語（生成、開始、削除、更新）へ置き換えた名前が無い。

FAIL：業務の語を使わず、形や処理から付けた名前の型か関数かメソッドが一つでもある。または、資料に英名がある語を、別の英名で書いている。

### no-guess-beyond-docs

重み: 3

PASS：コードの拒否（具体エラー）は、どれも業務知識の資料の拒む理由か、値の構造として必ず拒む値（空の識別子、形の違う値）に当たる。資料が提案や未決に回したもの（語、拒む理由、識別子）をコードにしたときは、報告にそれを仮置きとして挙げている。資料に無い業務の上限、状態、拒否、既定値を足していない。

FAIL：資料に根拠の無い業務の拒否、状態、上限、既定値がコードにある。または、提案や未決に回ったものを、報告で断らずに確定した業務の決まりとして書いている。

## 集約の形

### command-holds-decision

重み: 3

PASS：集約の公開メソッドは、資料のコマンドと、復元（`Restore*`）と、ほかの層が実際に読む値の取り出しだけである。受けるか拒むかの判断はコマンドの内側にあり、判断だけの公開メソッド（`Can*`、`Is*`、`Validate`、`Has*` の類）が無い。呼ぶ側が集約の状態や値を比べてからコマンドを呼ぶ必要が無い。

FAIL：判断だけを返す公開メソッドがある。または、コマンドを呼ぶ前に呼び手が判断しないと業務の決まりが守られない形になっている。

### decision-material-at-construction

重み: 3

PASS：コマンドの判断に要る集約の外の事実（件数、ほかの集約の状態の写し）は、集約の構造体を作るとき（初期状態の型か、復元した状態の型）に値として持たされ、コマンドがそれを読んで判断する。業務の時刻と採番した識別子は、コマンドの引数で受ける。材料が要らないなら、この条件は満たしたものとする。

FAIL：集約の外の事実を、構造体ではなく呼び手がコマンドの前に比べる形か、判断のための別の公開関数に渡す形にしている。

### initial-state-type

重み: 2

PASS：まだ保存されていない集約を、版を持たない初期状態の型で表し、生成のコマンドがそこから版1の状態の型を返す。保存された状態の型は、終端の状態も含めて版を持つ。「版が無い」を表す特別な値（版0、`NoVersion`、nil のポインタ）を作っていない。

FAIL：初期状態を特別な版の値や nil で表している。または、保存された状態の型が版を持たない。

### states-and-sum

重み: 2

PASS：資料の状態一つが保存された状態の型一つになる。保存された状態が二つ以上あるなら、それらを非公開のメソッドで閉じた interface（`//sumtype:decl`）にまとめ、その interface が保存された状態の受けうるコマンドを持ち、受けない状態は資料の拒む理由を返す。「その状態である」ことを `if` で確かめていない。コマンドは `<コマンド名>Result{Next, Event}` と error（何も変えないことがあるなら bool）を返し、版を進めるのはコマンドだけである。

FAIL：状態を列挙の値や bool で持って `if` や `switch` で分岐している。または、受けない状態の拒否が資料の拒む理由になっていない。または、コマンドの結果の形が崩れている。

### no-primitive-concepts

重み: 3

PASS：業務の概念（識別子、人数、時刻、状態、理由）を、フィールド、引数、戻り値、イベントのどこでも `string`、数、`bool`、`time.Time` のまま持たず、非公開フィールドの struct と検証する `New*` の値オブジェクトにしている。取りうる値が有限なら、型変換で外の値を作れない封じた型にしている。

FAIL：業務の概念をプリミティブのまま持つフィールド、引数、戻り値、イベントの値が一つでもある。または、`type X string` と `const` の組で列挙している。

### domain-knows-no-mechanism

重み: 2

PASS：ドメインの package は、時計を読まず（`time.Now` を呼ばない）、採番せず、記録（`log/slog`）、JSON、永続化、入口のプロトコルを import しない。永続化ポートがあるなら、完全な集約を返す `Find*` と error だけを返す `Apply*` だけを持つ。

FAIL：ドメインが時計、採番、記録、JSON、永続化、入口のどれかに触れている。または、永続化ポートに件数や存在の確認のような集約以外を返すメソッドがある。

## 公開面、コメント、書かずに済ませること

### public-only-used

重み: 3

PASS：実装の package（テストの前提を組む `builders/` を除く）の公開のシンボルは、資料のコマンドと振る舞い、それを確かめるテスト、ほかの層が読む契約（永続化ポートが読み書きする値、復元、イベントの取り出し）から呼ばれるものだけである。テストで内部を見るためだけの公開（`export_test.go`、テストでしか呼ばれない getter）が無い。`builders/` の Builder は、テストの前提を作るための置き場なので、テストからだけ呼ばれてよい。

FAIL：実装の package に、どこからも呼ばれない公開のシンボルか、テストで内部を見るためだけに足した公開のシンボルか `export_test.go` がある。

### comments-own-responsibility

重み: 3

PASS：コメントは、その型や関数自身の業務上の意味と責務だけを、業務の言葉で書いている。使う側の都合（「〜が呼ぶ」「〜のポートを満たす」「〜で注入する」）、別の package の型の名前、担わないものを誰が担うか、存在の理由を実装の事情に帰する断り書き（「資料に無い」「Go の都合」「実装の都合」）が無い。

FAIL：上のどれかに当たるコメントが一つでもある。

### lazy-reuse-before-writing

重み: 3

PASS：作業の前から repository にあったもので済む責務（同じ意味の値オブジェクト、エラーの分類、標準ライブラリの機能）を、探して使っている。使われない引数、呼ばれない分岐、将来のための枠や TODO、差し替える理由の言えない抽象（実装が一つしかない interface、設定化した変わらない値）を書いていない。

FAIL：作業の前からあった同じ責務のものか標準ライブラリで済むものを、自分で書き直している。または、上の将来のための足場か理由の無い抽象が一つでもある。

## テスト

### tests-carry-bdd

重み: 2

PASS：テストは、package を `<pkg>_test` にし、対象一つにテスト関数一つの表で書いている。資料の BDD を写すケースは、BDD の ID、見出し、gherkin を改変せずに `id`、`name`、`description` へ写し、資料に無いケースは資料風でない生成した id を使う。ドメインが主に担わない BDD（本人の確認、記録する側が守る重複や同時）に資料の ID を付けていない。

FAIL：BDD の ID か見出しか gherkin を変えて写している。または、資料に無いケースに資料風の番号を付けている。または、ドメインが観測できない BDD の ID を、ドメインのテストが名乗っている。

### tests-cover-decisions

重み: 2

PASS：コマンドがドメインで拒む理由ごとに、それを起こすケースがあり、数の境界があるなら境界の両側を確かめている。受けない状態で拒むことも、その状態の型のテストで確かめている。期待は、次の状態、発したイベントの値、具体エラーで書き、エラーの文言や bool で失敗を表していない。

FAIL：ドメインが拒む理由のどれかに、それを起こすケースが無い。または、境界の片側しか無い。または、エラーを文言で比べている。

### tests-real-values

重み: 1

PASS：ドメインのテストは、手書きの偽物や mock を使わず、`Restore*` と `New*` で組んだ本物の値だけで書いている。乱数と現在時刻を使わず、決定的な値を使っている。

FAIL：ドメインのテストに偽物か mock があるか、乱数か現在時刻を使っている。

## 細部

### files-and-errors

重み: 1

PASS：具体エラーは、それを返す package の `errors.go` に、作業の前からあった分類の package の `Define` で、資料の拒む理由の語を文言にして並んでいる。interface があるなら、自分の名前のファイルに単独で置かれている。

FAIL：標準の `errors.New` で業務の拒否を作っているか、文言が資料の拒む理由の語でない。または、interface と実装が同じファイルにある。
